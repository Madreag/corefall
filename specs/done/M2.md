# M2 — Micro Breach Fun Slice

## Status

`done`

## Intent

One 60-90 second playable scenario — `micro_breach` — that proves the M1 actor controller is fun to use under pressure: spawn → breach a soft barrier → fight or bypass one reactive enemy → reach extraction. Wins and losses both happen, both produce honest run bundles, and a scripted cfctl replay can drive both paths without human input.

## Player-facing behavior

- Player spawns at one end of a small map. An **objective banner** at the top of the HUD says "Breach the wall and reach the extraction zone." with a sub-line showing the current objective progress.
- A **soft destructible strip** (BreachStrip, M2's stand-in for M3 chunked terrain) blocks the path. The digger tool carves through it; refusal labels appear if the wrong tool is used. Events are forward-compatible with M3's chunked terrain so M10's replay viewer and any consumer can switch backends without rework.
- One **reactive enemy guard** (ReactiveGuard) is stationed near the breach. It has:
  - **Sight cone** (FOV + range; default 120° / 320 units).
  - **Hearing radius** (consumes `equipment.alarm_registered` from M1 weapon fire; default 480 units).
  - **Memory grid** (last-known player position decays after N ticks of no sightings; guard moves toward the last-known spot before returning to idle).
  - **Slow aim** (aim_settle_ticks before firing, e.g. 12 ticks at the default difficulty) — guard cannot snap-headshot the player.
  - **Imperfect fire** (miss_chance per shot, default 0.1) — even with a clean line of sight, ~10% of shots miss with a labeled reason.
  - **Reload mid-fight** if magazine empties.
  - **State machine**: `Idle → Alert → Engaged → Retreating → Dying → Dead`.
- The player can **kill the guard, sneak past, or breach + outrun** — three distinct win paths.
- **Difficulty presets** (`act.settings.set { ai_difficulty: "cakewalk" | "tough_crowd" | "veteran" }`): each preset adjusts guard HP, aim_settle_ticks, and miss_chance per DR-050 onboarding so new players can ramp up. Defaults to `tough_crowd`.
- **Timer**: 60-90 seconds, configurable per scenario. HUD countdown changes color: green >30s, yellow 10-30s, red <10s.
- **HUD** shows: objective banner + sub-line + timer + player HP + selected item + guard HP (when in sight) + last-important-event ticker + (with `--ai-debug`) guard's current intent label floating above the guard sprite ("ALERT: heard shot", "ENGAGING", "RELOADING").
- **Win** = reach extraction alive within timer. **Lose** = player dies, timer expires, OR objective fails. **Aborted** = player invokes `act.player.abort` (forfeit).
- Both win + loss outcomes emit a structured `mission.mission_resolved` event with `result` + typed `loss_reason` + `parent_event_id` chain pointing at the trigger event (death → status_changed → wound → projectile_hit → guard's weapon_fired).
- **Tutorial-safety policy** (per DR-023 + DR-018): scenarios with `tutorial_safety=true` demote lethal damage to KO so new players can finish their first session. M2 defaults to `false` (lethal allowed); the onboarding-mission variant sets it `true`.
- On loss, the HUD offers a **"show me why" prompt** that hands off to the M10 replay viewer at the divergence event (per DR-023 onboarding handoff).
- The guard **drops its weapon on death** at hand position with toss velocity (per DR-018 death-meaning ladder + CCCP `Actor.cpp:1215`). The dropped weapon is picked up by `act.player.pickup` (placeholder; full pickup ladder is M13).

## Acceptance criteria

### Mission state machine + outcomes

```gherkin
Scenario: Win path — kill guard then extract
  Given a fresh micro_breach scenario at tough_crowd difficulty
  When the cfctl script micro_breach_win.cfctl.json runs
  Then the player breaches the wall (terrain.terrain_carved count ≥ N)
  And kills the guard (guard's actor.actor_status_changed to DEAD fires)
  And reaches the extraction zone within the timer
  And mission.objective_completed fires for "reach_extraction"
  And mission.mission_resolved fires with result=won, parent_event_id (cause = objective_completed)
  And cf-e2e --expect mission.result=won passes
  And the run bundle validates (errors=0)

Scenario: Win path — stealth (sneak past without firing)
  Given a fresh micro_breach scenario
  When the cfctl script micro_breach_stealth.cfctl.json runs (digs through wall, never fires)
  Then the guard NEVER transitions to Engaged (no equipment.alarm_registered consumed)
  And no ai.target_acquired event fires
  And the player reaches extraction
  And mission.mission_resolved fires with result=won, parent_event_id chain shows no combat
  And cf-e2e --expect mission.result=won, ai.state_changed.count≤2 passes (Idle → Alert from breach noise → back to Idle)

Scenario: Loss path — player dies
  Given a fresh micro_breach scenario
  When the cfctl script micro_breach_loss.cfctl.json runs (player walks into guard's LOS, stays still)
  Then the guard reaches Engaged
  And guard fires multiple shots (equipment.weapon_fired.count ≥ N)
  And the player's HP reaches 0 (actor.actor_status_changed to DEAD)
  And mission.mission_resolved fires with result=lost, loss_reason=PlayerDead, parent_event_id linked to player's status_changed → guard's weapon_fired
  And cf-e2e --expect mission.result=lost, mission.loss_reason=PlayerDead passes

Scenario: Loss path — timer expires
  Given a fresh micro_breach scenario with timer=60s
  When the player waits without progressing for 60 seconds
  Then the timer reaches 0
  And mission.mission_resolved fires with result=lost, loss_reason=TimerExpired
  And cf-e2e --expect mission.result=lost, mission.loss_reason=TimerExpired passes

Scenario: Aborted — player forfeits
  Given a fresh micro_breach scenario
  When cfctl invokes act.player.abort
  Then mission.mission_resolved fires with result=aborted, loss_reason=Aborted
  And cf-e2e --expect mission.result=aborted passes

Scenario: Mission state surface
  Given a running mission
  Then MissionState contains: id, status (InProgress), started_at_tick (set on first tick), last_transition_tick (updates on every state change), current_objective_id, completed_objectives[], failed_objectives[], loss_reason (None while InProgress), timer_ticks_remaining, timer_total_ticks
  And cfctl observe.mission returns the full state

Scenario: Loss reasons are typed enum (not strings)
  Given the LossReason enum
  Then it has variants: PlayerDead, TimerExpired, ObjectiveFailed { id, reason }, Aborted, ReactorDestroyed (future)
  And each has an as_str() method that produces the stable replay label
  And mission.mission_resolved.loss_reason serializes as the as_str() value, never a raw string literal
  (DR-002 stable-vocabulary contract)
```

### Objective grammar

```gherkin
Scenario: Objective lifecycle events
  Given the scenario starts (tick 0)
  Then mission.mission_started fires once with mission_id, seed, scenario_id
  And mission.objective_started fires for "breach_wall" with objective_id, kind=ReachZone (target = breach exit point), parent_event_id (cause = mission_started)
  And mission.objective_started fires for "reach_extraction" with kind=ReachZone

Scenario: Objective progress updates
  Given the player is carving the breach wall
  When carve progress reaches 25%, 50%, 75%, 100%
  Then mission.objective_updated fires at each milestone with progress: 0.25, 0.5, 0.75, 1.0
  When carve completes
  Then mission.objective_completed fires for "breach_wall"

Scenario: Objective fail-sensor
  Given the "reach_extraction" objective has a fail_sensor: timer_remaining_ticks==0
  When the timer reaches 0 while extraction is incomplete
  Then mission.objective_failed fires with objective_id="reach_extraction", reason="timer_expired"
  And mission.mission_resolved fires with result=lost

Scenario: Objective paused (tutorial mode)
  Given a scenario with tutorial_safety=true
  When the player triggers a tutorial-modal that consumes input
  Then mission.objective_paused fires for the current objective
  And the timer does NOT advance while paused
  When the modal closes
  Then mission.objective_resumed fires
  And the timer resumes

Scenario: Tutorial-safety demotes lethal damage to KO
  Given a scenario with tutorial_safety=true
  When the player would take lethal damage (HP → 0)
  Then actor.actor_status_changed caps at DYING (does NOT transition to DEAD)
  And the player can recover (HP regen or scripted heal) without restarting the mission
  And mission.mission_resolved does NOT fire with loss_reason=PlayerDead
```

### Reactive guard AI (DR-008 + DR-022 subset)

```gherkin
Scenario: Guard state machine has 6 states with reason labels
  Given a ReactiveGuard
  When the player enters its sight cone
  Then ai.state_changed fires with from=Idle, to=Alert, reason="saw_player_in_cone", parent_event_id=<perception_signal>
  When the player remains in LOS for aim_settle_ticks
  Then ai.state_changed fires with from=Alert, to=Engaged, reason="target_acquired"
  When the guard's HP drops below 30% (configurable retreat threshold)
  Then ai.state_changed fires with to=Retreating, reason="low_hp"
  When the guard's HP reaches 0
  Then ai.state_changed fires with to=Dying, reason="killed_by_<source_actor_id>"
  After 1000ms dwell
  Then ai.state_changed fires with to=Dead

Scenario: Perception — sight cone
  Given a ReactiveGuard with sight_cone (120° FOV, range 320 units)
  When the player enters the cone within range
  Then ai.perception_signal fires with kind="sight", source_id=player, confidence=1.0, line_of_sight=clear
  When the player walks behind cover (LOS blocked)
  Then ai.perception_signal fires with kind="sight_lost", line_of_sight=blocked, last_known_pos=<player's last visible pos>

Scenario: Perception — hearing alarm (consumes M1 alarm_registered)
  Given a ReactiveGuard with hearing_radius=480
  When the player fires the rifle within 480 units (equipment.alarm_registered)
  Then ai.perception_signal fires with kind="hearing", source_id=player, source_pos, confidence (decays with distance), parent_event_id=<alarm_registered>
  And ai.state_changed fires Idle → Alert if currently Idle

Scenario: Perception — memory grid (last-known position decay)
  Given the guard sighted the player at position P at tick T
  And lost LOS at tick T+10
  When memory_decay_ticks (default 300 = 5 seconds at 60Hz) elapse
  Then ai.perception_signal fires with kind="memory_decayed", actor_id=player
  And the guard returns to patrolling/idle (no longer searches P)

Scenario: Slow aim (aim_settle_ticks before firing)
  Given a ReactiveGuard with aim_settle_ticks=12 (tough_crowd difficulty)
  When the guard transitions to Engaged
  Then no equipment.weapon_fired event fires for 12 ticks (~0.2s at 60Hz)
  And ai.tactic_chosen fires with tactic="aim_settle", reason="initial_acquisition"
  After 12 ticks
  Then equipment.weapon_fired fires with parent_event_id=<tactic_chosen>

Scenario: Imperfect fire (miss_chance per shot)
  Given a ReactiveGuard with miss_chance=0.1 (tough_crowd)
  When the guard fires 100 shots at a stationary target
  Then approximately 10 shots miss (within stochastic bounds; seeded RNG)
  And each miss emits ai.missed_shot_reason with reason ∈ {recoil_deviation, target_moved, lucky_dodge, occlusion}
  And misses use the ENGINE RNG (not thread_rng); same seed → same outcome

Scenario: Reload mid-fight
  Given the guard's magazine empties during Engaged
  Then equipment.weapon_reload_started fires
  And ai.state_changed fires with state=Engaged, reason="reloading" (state unchanged; reason updates)
  And the guard does not fire during reload_duration_ticks
  When reload completes
  Then firing resumes

Scenario: Stuck recovery
  Given a guard pursuing the player
  When the guard cannot reach the target within 60 ticks (no path)
  Then ai.stuck_state_changed fires with stuck_time_ticks=60, blocker_id (e.g. terrain wall or player), old_state=Engaged, new_state=Engaged_Stuck
  Then ai.recovery_action fires with action ∈ {wait, retreat, find_cover, switch_target, dig_through (M3+)}, reason
  And the guard takes the recovery action

Scenario: AI difficulty preset round-trip
  Given act.settings.set { ai_difficulty: "veteran" }
  When the engine applies the patch
  Then the guard's hp=120, aim_settle_ticks=6, miss_chance=0.05, sight_range=480, hearing_radius=600
  And cfctl observe.ai.<guard_id> returns the same values
  And run_manifest.json.settings.ai_difficulty="veteran"

Scenario: Guard drops weapon on death (DR-018)
  Given a ReactiveGuard armed with a rifle
  When the guard's HP reaches 0
  Then actor.actor_status_changed fires (DYING)
  And actor.inventory_dropped fires with item_id=guard's rifle, hand_position, toss_velocity, parent_event_id=<status_changed>
  And the rifle becomes a loose pickup (placeholder; full pickup ladder at M13)

Scenario: AI debug labels (--ai-debug flag)
  Given cf-app --ai-debug
  When the guard's state changes
  Then a floating text label above the guard sprite shows the current state + reason ("ALERT: heard shot", "ENGAGING", "RELOADING", "STUCK: blocked")
  And the label updates within 1 tick of state change
  And without --ai-debug the label is hidden
```

## Notes for the implementer

### Architecture rules

- **AI intent does NOT flow through ControlIntent.** ReactiveGuard uses a separate `EnemyTickReport` (or `cf-ai::AiIntent`) struct. This is by design: player intent has edge flags + analog input; AI intent has chosen tactic + target + reason. Different shapes. Don't try to unify them at M2 — the layered DR-008 architecture cleanly separates them.
- **Per CCCP `Controller.cpp:196-208` AI throttle**: AI updates don't have to run every tick. M2 default = AI tick every 3 sim ticks (~20Hz at 60Hz sim), distributed by actor id modulo. **BUT** emergency high-priority updates MUST run every tick (e.g. taking damage triggers an immediate state evaluation). Per CCCP TODO "missing high-priority tick" — we fix this at M2 by exposing `force_ai_update_this_tick` flag.
- **Per CCCP `NativeHumanAI.lua` coroutine pattern**: behavior changes (Idle → Alert → Engaged) cancel the prior behavior cleanly. Use Rust enum state + explicit transition function; do NOT use threads or coroutines.
- **Mission state machine is authoritative**: never compute mission status from observation; always read MissionState directly. cfctl observe.mission returns the live struct.

### Replay envelope + cause chains

- All M2 events use the M0/M1-locked `prototype-recorder-event.v0.1` envelope.
- **Every event carries `parent_event_id`**. The richest chain at M2:
  - `mission.mission_started` (root) → `mission.objective_started` × N
  - `input.intent_received` → `act.player.dig` → `terrain.terrain_carved` → `mission.objective_updated` (progress) → `mission.objective_completed`
  - Guard side: `equipment.alarm_registered` (player fire) → `ai.perception_signal` (hearing) → `ai.state_changed` (Idle→Alert) → `ai.target_acquired` (LOS gained) → `ai.tactic_chosen` (aim_settle) → `equipment.weapon_fired` (guard) → `combat.projectile_spawned` → `combat.projectile_hit_mo` (player) → `combat.wound_added` → `actor.actor_status_changed` (player DYING) → `actor.inventory_dropped` → `mission.objective_failed` (player_dead) → `mission.mission_resolved` (loss_reason=PlayerDead)
- **Stable IDs**: never use raw pointers or pooled MOIDs for replay identity. Use cf-replay's `record_id` layer.
- **Don't bypass dirty-tracking** when BreachStrip mutates terrain: call `add_updated_material_area` for every edit, even though M2's terrain is a tile field rather than full chunked grid.

### Pitfalls / things that have bitten us before

- **AI uses thread_rng**: replay determinism breaks instantly. Use the engine seeded RNG for miss_chance, target_pick, recovery_action. AGENTS.md rule + project bug history.
- **Mission state computed from observation**: race conditions + drift. ALWAYS read MissionState directly; never recompute from events.
- **Path-refresh starvation** (CCCP TODO): if path requests are active every frame, pathfinder updates pause. M2 doesn't have pathfinder yet; M22+ must fix this when it lands.
- **String-literal loss reasons**: DR-002 stable-vocabulary contract. Use the typed enum's `as_str()`.
- **Forgetting `parent_event_id`**: M10 cause-chain walking returns `ParentMissingFromBundle`. Code review: every event-emit site must set parent_event_id (or explicitly mark `unknown_cause` with a reason).
- **AI updates running every tick at sim_rate**: too expensive at squad scale. Throttle per actor_id mod tick (CCCP pattern); but expose force-update for danger states.
- **Memory grid leak**: don't grow unbounded. Cap at N entries per guard; oldest decays first.
- **60-90 second window is real**: if scenarios consistently run >90s, the cfctl scripts are too long. Cut steps, not the contract.
- **No emoji in any HUD or replay text** (project rule).
