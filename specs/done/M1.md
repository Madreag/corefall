# M1 — Actor Controller And Sim Core

## Status

`active`

## Intent

One human-piloted actor is fully playable on the native engine: moves, jumps, aims, fires, reloads, digs, swaps inventory, takes damage through a body-status state machine, and emits the full input → intent → sim → event ladder so every action is reachable from `cfctl` and verifiable in the run bundle.

## Player-facing behavior

- WASD moves the actor, mouse aims, click fires, R reloads, Space jumps, G digs, 1-4 select inventory slot, Backspace resets to spawn.
- The actor has a body-status state machine: STABLE → UNSTABLE → DOWNED → DYING → DEAD with cause labels and dwell-time on each transition (DYING → DEAD takes 1000ms so death has texture, not a hard cut — per CCCP `Actor.cpp:1229`).
- HUD shows ammo line with reticle state (READY/RELOADING/EMPTY/COOLDOWN), status, selected item, last important event.
- Stability scalar (0.0-1.0) decreases on recoil and hard landings; recovers when grounded; below 10% the actor enters a knockdown stun.
- Mass-based physics: heavier actors accelerate / decelerate slower and resist knockback proportionally.
- Projectiles inherit the actor's velocity at fire time (running shots arc; falling shots drift).
- Each shot emits an acoustic noise event with a loudness radius proportional to weapon damage so AI/audio downstream can react.
- **Sharp aim** (per CCCP `AHuman.cpp:1779` + Soldat): when the player holds aim while stable, slow, and equipped, aim deviation tightens. Sharp aim is reset by jump, reload, item swap, knockdown, or movement above a walking threshold — and the reticle visibly snaps wide so the player sees WHY their next shot is inaccurate.
- **Movement accuracy bloom** (per OpenSoldat `Sprites.pas:4870`): the reticle grows from movement, recoil, airborne state, and reload. Running multiplies bloom by ~7×, jumping/jetting by ~7×, airborne/prone-transition by ~3×, standing/walking by 1×. Player sees the cause through reticle size, not hidden math.
- **Inventory drop on dying** (per CCCP `Actor.cpp:1215`): when the actor enters DYING, carried weapon (and gold/credits if any) drops at the actor's hand position with toss velocity. Emits `actor.inventory_dropped` event so the replay can show what fell where.
- **Overlay-captured-control feedback** (per CCCP `Controller.cpp:280` pie-menu lesson): when a UI surface captures input (settings panel, debrief prompt, future pause/menu), the HUD shows a "CONTROLS CAPTURED" badge so the player knows their inputs aren't reaching the actor.
- All inputs produce structured `input.intent_received` events with edge-trigger flags; the same sim path runs whether input came from human or `cfctl`.
- The actor can be played for at least 5 minutes without crashes, and the resulting run bundle replays headlessly with identical checksums.

## Acceptance criteria

### Core playability

```gherkin
Scenario: Solo play for 5 minutes without crash
  Given a fresh m1_actor_range scenario
  When the player moves, jumps, fires, reloads, digs, and swaps items continuously for 5 minutes (18000 ticks at 60Hz)
  Then no panic occurs
  And the run bundle's events.jsonl is well-formed
  And system.run_finished outcome=clean
  And the run-bundle checker (prototype_run_check.py) returns errors=0

Scenario: 60Hz vs 120Hz determinism
  Given the same cfctl script m1_move_jump_fire_reload.cfctl.json
  When run once with --tick-rate-hz 60 and once with --tick-rate-hz 120
  Then both runs complete cleanly
  And summary.final_sim_checksum is stable for each tick rate (replays match within tick rate)
  And the 120Hz run's wall-clock duration ≈ same real seconds as the 60Hz run (sim time matches)

Scenario: Headless smoke without window
  Given cf-app --headless-smoke --scenario m1_actor_range
  When the run completes
  Then run_manifest.json + events.jsonl are valid
  And no Bevy window is opened (CI safety)
```

```gherkin
Scenario: All M1 control methods reachable via cfctl
```

### Body status + damage ladder

```gherkin
Scenario: Body status state machine with cause labels
  Given an actor at full HP
  When projectile damage drops HP below the UNSTABLE threshold
  Then actor.actor_status_changed fires with from=STABLE, to=UNSTABLE, cause="projectile_hit", parent_event_id=<projectile_hit_event>
  When HP drops below the DOWNED threshold
  Then actor.actor_status_changed fires with to=DOWNED and a cause label
  When HP reaches 0
  Then actor.actor_status_changed fires with to=DYING and a cause label
  And after the DYING dwell timer (1000ms / 60 ticks at 60Hz, configurable) expires
  Then actor.actor_status_changed fires with from=DYING, to=DEAD

Scenario: INACTIVE status for tutorial pause / cutscenes
  Given an actor in a scenario with tutorial_safety=true
  When the activity script sets the actor INACTIVE
  Then the actor skips control intent consumption
  And cfctl observe.actor.status returns "INACTIVE"
  And no actor.actor_status_changed → DYING transition occurs even if HP would drop below 0

Scenario: Travel-impulse damage on UNSTABLE actor (per CCCP Actor.cpp:1199)
  Given an UNSTABLE actor with stability < 1.0
  When a travel impulse exceeds travel_impulse_damage_threshold (default 100)
  Then the actor takes damage = max((|impulse| - travel_impulse_damage) / (gib_impulse_limit - travel_impulse_damage) * max_hp, 0)
  And actor.actor_status_changed may transition (UNSTABLE → DOWNED → DYING) with cause="travel_impulse"
  And a body-hit sound event is emitted
  And STABLE actors do NOT take travel-impulse damage (they only become UNSTABLE first)

Scenario: Inventory drop on DYING (per CCCP Actor.cpp:1215)
  Given an actor carrying a rifle with HP=5
  When the actor takes lethal damage (HP→0)
  Then actor.actor_status_changed fires with to=DYING
  And actor.inventory_dropped fires with item_id, hand_position, toss_velocity, parent_event_id=<status_event>
  And the rifle becomes a loose pickup at the hand position
  And subsequent firing intent is rejected ("no weapon")

Scenario: Mission-critical flag prevents instant kill
  Given an actor with mission_critical=true
  When lethal damage applies
  Then chassis_stage_changed / status_changed caps at DYING (does not reach DEAD)
  And mission director (M1.5+) can react to "critical actor downed" before final loss
```

### Movement + aim feel (DR-055 game-feel)

```gherkin
Scenario: Mass-based physics
  Given two actors of different mass (light=50kg, heavy=200kg)
  When both take the same horizontal recoil impulse
  Then the heavy actor's resulting velocity is ~1/4 of the light actor's (per F=ma)
  When both fall from the same height
  Then their landing impulse scales linearly with mass

Scenario: Stability decreases on recoil, recovers on ground
  Given an actor with stability=1.0
  When the player fires the rifle
  Then stability drops by recoil_cost = recoil_impulse / 200 (so ~120 impulse → ~0.06 cost)
  When the player stops firing and stays grounded for 60 ticks
  Then stability recovers toward 1.0 at stability_recovery_rate per tick

Scenario: Knockdown stuns the actor with all-input rejection
  Given stability < 0.1
  When the actor takes another destabilizing hit (recoil or landing impulse > 100)
  Then the actor enters Stance::KnockedDown for 18 ticks
  And physics.authority_changed fires with from=animation, to=ragdoll
  And during knockdown ALL input is rejected: move, aim, fire, reload, jump, dig, select_item are no-ops
  And the HUD STANCE line reads "KNOCKED_DOWN"
  And after 18 ticks control returns and physics.authority_changed fires (back to animation)

Scenario: Sharp aim builds when stable, slow, equipped (per CCCP AHuman.cpp:1779)
  Given a STABLE actor with selected_slot=rifle, velocity_magnitude < walk_threshold
  When the player holds act.player.sharp_aim for N ticks
  Then sharp_aim_progress increases linearly from 0 → 1.0 over (sharp_aim_build_ticks=30) ticks
  And the reticle visibly tightens (bloom multiplier < 1.0)
  And cfctl observe.actor.sharp_aim_progress returns the same value

Scenario: Sharp aim invalidated by movement / jump / reload / item swap / knockdown
  Given an actor with sharp_aim_progress=1.0
  When ANY of: velocity exceeds walk_threshold / act.player.jump / act.player.reload / act.player.select_item / Stance becomes KnockedDown
  Then sharp_aim_progress snaps to 0
  And actor.sharp_aim_invalidated fires with reason ∈ {moved, jumped, reloading, item_swap, knockdown, unstable}
  And the HUD reticle visibly blooms wide

Scenario: Movement accuracy bloom (per OpenSoldat Sprites.pas:4870)
  Given an actor firing while moving in different states
  Then the reticle's bloom multiplier follows: standing=1.0×, walking=1.0×, running=7.0×, jumping=7.0×, jetting=7.0×, airborne=3.0×, prone-transition=3.0×
  And the bloom is visibly proportional (player can SEE the reticle grow)
  And actor.bloom_factor is on ActorObservation for AI/UI consumers

Scenario: Recoil decays over time and alternates side (per CCCP HDFirearm.cpp:891)
  Given an actor with recoil_accumulator=120
  When 60 ticks pass without firing
  Then recoil_accumulator decays toward 0 at recoil_decay_rate per tick
  When the actor fires multiple shots
  Then alternating shots add positive/negative angular recoil so the muzzle drifts predictably (not symmetric chaos)
```

## Out of scope

- Reactive enemy AI — M1.5 (M1 emits `equipment.alarm_registered` so M1.5 AI can consume; no AI consumer at M1)
- Mission/objective state — M1.5 (`mission.objective_*` events; M1 has no objective)
- Per-zone wound model + AEmitter wound emitters that bleed/spark — M5 chassis (M1 emits `wound_added` as scalar HP delta only)

## Notes for the implementer

### Architecture

- **Update order matters** (per CCCP `Actor::FullUpdate`): per-tick sequence is **(1) PreControllerUpdate** (path requests) → **(2) Controller::Update** (consume player/AI/replay/script intent into ControlIntent resource) → **(3) Actor::Update** (status, stability, travel-impulse damage, DYING dwell, inventory fallout) → **(4) Movement/equipment update** (movement, aim, fire, reload, item swap) → **(5) Device update** (rounds, recoil, sounds, alarms) → **(6) Terrain response** (penetration / dirty regions; M2 owns the terrain side). M1 must respect this ordering or replay determinism breaks.
- **`IntentSource` enum has 4 variants but only Player + Replay emit at M1.** `Ai` is reserved for M1.5 (ReactiveGuard uses a separate `EnemyTickReport` path that's NOT routed through ControlIntent — by design, since AI intent has different shape than player intent). `Script` is reserved for M5+ scripted equipment hooks (DR-006 OPEN).
- **Same sim path for human + cfctl + replay** is non-negotiable. `cf-app` keyboard input goes through `cf-control` JSON-RPC — no shortcut path. This is what makes the deterministic-replay channel work and what makes AI substitutability real.

### Sim numbers / formulas (anchor to source code)

- **Stability cost on recoil**: `cost = recoil_impulse / 200` (see cf-actor/sim.rs:574 reference). 200 is the magic divisor that gives a standard rifle (~120 impulse) a ~0.06 stability cost per shot.
- **Stability quantization**: stability is included in the per-tick checksum via `quantize_f32` to int32. Do NOT change quantization granularity without bumping the checksum schema (M3A owns checksum cadence; M1 just feeds it).
- **Knockdown threshold**: `stability < 0.1` AND `incoming_impulse > 100` triggers Stance::KnockedDown for 18 ticks (~0.3s at 60Hz). At 120Hz the dwell is still 18 ticks (i.e. ~0.15s real time) — for "real-time-stable" feel, multiply by tick_rate ratio if needed (open question — recommend keeping tick-count for first cut).
- **Travel-impulse damage formula** (CCCP `Actor.cpp:1199`): `damage = max((|impulse| - travel_impulse_threshold) / (gib_impulse_limit - travel_impulse_threshold) * max_hp, 0)`. STABLE actors are immune; only UNSTABLE takes travel-impulse damage.
- **DYING dwell** (CCCP `Actor.cpp:1229`): default 1000ms = 60 ticks at 60Hz. Configurable per scenario for tutorial / iron-man modes.
- **Loudness radius** (cf-actor/sim.rs:574): `480.0 * (damage / 10.0).clamp(1.0, 3.0)` — gives a baseline-damage rifle ~480 unit radius, scaling up to ~1440 for high-damage weapons.
- **Reticle bloom multipliers** (per OpenSoldat `Sprites.pas:4870`): standing/walking=1×, running/jumping/jetting=7×, airborne/prone-transition=3×. Implemented as a `bloom_factor` field on ActorObservation.

### Replay envelope + cause chains

- All M1 events go through the `prototype-recorder-event.v0.1` envelope (locked at M0; DR-002 closure). Don't change the envelope shape at M1.
- **Every event with a logical cause MUST set `parent_event_id`.** Slice A list (per `replay-recorder-slice-a` + CCCP code-walk):
  - `input.intent_received` (root; no parent)
  - `equipment.weapon_fired` (parent = `input.intent_received` for fire press)
  - `combat.projectile_spawned` (parent = `weapon_fired`; can spawn N children for multi-pellet rounds)
  - `combat.projectile_hit_mo` / `terrain.terrain_carved` (parent = `projectile_spawned`)
  - `combat.wound_added` (parent = `projectile_hit_mo`; M1 emits scalar wound; M5 chassis adds zone/layer)
  - `actor.actor_status_changed` (parent = `wound_added`)
  - `actor.inventory_dropped` (parent = `actor_status_changed` to DYING)
  - `equipment.alarm_registered` (parent = `weapon_fired`; consumed by M1.5+ AI perception)
- **Stable actor IDs**: do NOT use raw pointers or pooled MOIDs as event identity (CCCP `MovableMan.cpp:126-143` warning — pooled memory makes stale pointers re-allocate at old addresses). Use `cf-replay::record_id` layer for stable identity across the run.

### Pitfalls / things that have bitten us before

- **5-minute is literal**: 60-second loops are not equivalent — tick count + checksum cadence are real numbers in `run_manifest.json`. Build a `m1_5min_endurance.cfctl.json` script that runs 18000 ticks and validates.
- **Edge flags**: `clear_edges()` runs after consumption per tick. If a press+release happens within one tick, it MUST still register one consumed press. Test scenario covers this.
- **NaN propagation**: ALL floating-point inputs from cfctl must check `is_finite()` BEFORE applying. NaN in velocity poisons the checksum.
- **Tick-rate-stable timing**: any "N ticks" duration (knockdown=18, DYING dwell=60, sharp_aim_build=30) should be re-thought when tick_rate changes. Open question whether to use real-seconds or fixed tick count; M1 default is fixed ticks, document the tradeoff.
- **HUD vs Sim ordering**: HUD reads ActorObservation AFTER sim tick; never read mid-tick. Otherwise the player sees inconsistent state.
- **No emoji in any HUD or replay text** (project rule).
