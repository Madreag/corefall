# M2 — Pixel Terrain And Materials

## Status

`active`

## Intent

Mutable chunked pixel terrain with 8 launch materials. The player can dig a soft-material wall, the change is visible within one frame, replay-recorded with material id and bbox, and respected by the simple physics. Material affordances (hardness, anchorability, hazard, path-cost) are data-driven and queryable.

## Player-facing behavior

- The world is made of pixels grouped into 256×256 chunks. Each pixel has a material id (air / dirt / concrete / metal-nohook / hazard / loose_fill / repair_fill / anchor).
- The digger tool carves dirt fast, concrete slowly, refuses metal-nohook with a reason label.
- Carving is visible in the next frame (dirty regions trigger re-render).
- Pixel debris particles spawn at the carve site.
- A material-overlay toggle (`act.player.toggle_material_overlay` / hotkey M) tints every material a distinct color so the player can see what's around them.
- Hazard tiles damage the player on touch.
- Anchor materials accept tethers; non-anchorable materials refuse with a labeled reason.

## Acceptance criteria

```gherkin
Scenario: Dig affordances respect material hardness
  Given the player stands on dirt next to a dirt wall, then a concrete wall, then a metal-nohook wall
  When the player digs each in turn
  Then dirt carves in <0.5s of in-game time
  And concrete carves in 5-10x the dirt time
  And metal-nohook emits tool_refused with reason="material_not_diggable"

Scenario: Carve event carries bbox + material id + count
  Given a player digging dirt
  When the carve completes
  Then terrain.terrain_carved fires
  And the payload contains bbox=(x,y,w,h), material_id=1 (dirt), pixel_count>0, mask_id (stable hash of carve mask)

Scenario: Dirty regions render within one frame
  Given a freshly-carved chunk
  When the next render frame runs
  Then the carved area shows the new material (air or background)
  And no stale chunk pixels remain visible

Scenario: All 8 launch materials read correctly under overlay
  Given the player is in m2_material_lane scenario
  When the player toggles the material overlay
  Then every pixel of the 8 materials renders with the correct color_hex from the registry
  And the overlay legend lists all 8 materials with their display_name

Scenario: Hazard tile damages on contact
  Given the player walks into a hazard tile
  When the contact is registered
  Then terrain.hazard_contact_or_avoidance fires with actor_id + tile_position + result="damaged"
  And the player's HP drops
  And actor.actor_status_changed fires if HP crosses a status threshold

Scenario: Anchor material accepts/refuses with reason
  Given the player attempts to anchor on dirt (anchorable=true)
  Then terrain.anchor_material_result fires with result="accepted"
  When the player attempts to anchor on metal-nohook (anchorable=false)
  Then terrain.anchor_material_result fires with result="refused", reason="material_not_anchorable"

Scenario: Replay reconstructs terrain at any tick
  Given a 2-minute m2_material_lane bundle with 50 carve events
  When cf-headless replay <bundle> runs
  Then the per-tick terrain checksum matches at every cadence point
  And the final terrain state hash matches the live run

Scenario: Material-overlay observe surface
  Given a running scenario
  When cfctl observe.terrain runs
  Then the response includes chunk_count, dirty_chunk_count, and material_distribution {id: pixel_count}
  When cfctl inspect.terrain.chunk x=5,y=3 runs
  Then the response includes the chunk's full material grid

Scenario: Rifle chips dirt pixels
  Given the player fires the rifle at a dirt wall
  When projectile impact registers
  Then terrain.terrain_carved fires with material_id=1, small bbox, pixel_count<10
  And terrain.terrain_penetration_threshold fires with the impulse vs hardness comparison

Scenario: Dirty region batch event per tick
  Given multiple chunks dirtied in one tick
  When the tick ends
  Then terrain.terrain_dirty_region_batch fires once with all dirty chunks listed

Scenario: cf-mod validates the material registry
  Given content/materials/material_registry.json
  When `cargo run -p cf-mod -- validate content/materials/` runs
  Then exit code is 0
  And errors=0
  When the file is corrupted (bad schema_version)
  Then exit code is non-zero with a structured error
```

## Out of scope

- GPU-assisted carving compute shader — BP4 perf optimization (CPU path is the M2 floor)
- Active material kernel (cellular automaton, sand falls, water pools) — M5.6
- Active reaction table (water+fire→steam) — M5.6
- Pathfinder consuming material path-cost — M6+
- AI consulting terrain materials — M6
- Collapse / structural support rules — M5.5+ (prototype-only at BP3 by design)
- Tether tool implementation — M5.5+ (anchor material exists; tool comes later)

## Dependencies

- M1 actor controller (must be done): player can move + use tools
- M1.5 BreachStrip event surface (must be done): terrain.terrain_carved schema established

## Notes for the implementer

- `material_registry.json` already exists with 8 materials at `game/content/materials/material_registry.json`. Use it as the source of truth; do NOT hardcode material defs in Rust.
- Chunk size 256×256 is the spec; do NOT change without bumping `MATERIAL_SCHEMA_VERSION` and updating chunk dirty-tracking math.
- Dirty-region tracker emits ONE batch event per tick (not per chunk) — see acceptance scenario.
- `mask_id` on carve events is a stable hash so two replays of the same carve produce the same mask_id (deterministic).
- The 1280×720 perf target sits with T-PERF gate. Don't fail M2 if perf isn't formally measured; flag it as `[~]` and let T-PERF measure it.
