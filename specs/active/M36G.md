# M36G — Performance Benchmark Suite + Per-Platform Reference Numbers + Regression Gates + Frame-Time Profiling

## Status

`active`

## Intent

M36G ships the **measurement authority layer** beneath M36C (server tier + per-tick budget) and M36D (GPU/CPU parity): a permanent benchmark suite at `game/crates/cf-bench/` that exercises every hot path inventoried in DR-054 against a locked-in set of per-platform reference numbers (Workstation, Apple Silicon, Linux VPS, Apple Mini Lab cluster), enforces p95/p99 latency budgets as machine-checkable PR gates, surfaces per-subsystem percentile dashboards via cf-tools, integrates a per-tick frame-time profiler producing per-system breakdown timelines + flamegraphs, accounts GPU/CPU usage per loaded mod, and runs auto-bisect against `main` on every regression so the offending commit is named in the PR comment without human triage. M36C declared the budget; M36D enforced GPU parity; M36G is the daily-driven CI engine that proves the budget holds tick after tick, commit after commit.

## Canonical ownership

Owns the `cf-bench` crate (already partially declared in M36D for GPU/CPU parity matrix), the per-platform reference number ledger, the per-PR p99 regression gate, the per-subsystem percentile dashboard generators in `cf-tools`, the frame-time profiler (per-tick timeline + per-system breakdown + per-mod accounting), and the auto-bisect bot that comments on regressing PRs. DR-054 declared the optimization stack + hot path inventory; M36C declared the per-tick budget; M36G is the perpetual machine harness that verifies both. Performance benchmarks for any new subsystem added after M36G MUST register a `cf-bench` case as a prerequisite for merge.

## Operator-facing + indirectly-player-observable behavior

- **Operator: per-platform reference numbers locked in `cf-bench-reference.ron`.** Each subsystem × each reference platform has a `(p50, p95, p99, max)` latency baseline in microseconds; baselines updated by an explicit ledger commit, never silently.
- **Operator: PR comment surfaces regressions in plain English.** Every PR run posts a comment: "Subsystem `cf-material::kernel_ca` regressed on Linux VPS: p99 was 1.42 ms, baseline 1.20 ms, +18.3%. Bisected to commit `abc1234` (auto-bisect 7 candidates, 11 min wall clock)."
- **Operator: dashboard per-subsystem percentiles browsable.** `cf-tools bench dashboard --subsystem cf-material --window 30d` renders an HTML page with rolling p50/p95/p99 charts per platform; trend line annotated with PR merge points.
- **Operator: frame-time profiler live.** `cfctl observe.perf.frame_timeline --ticks 60` returns a JSON timeline of every system's wall-clock slice during the last 60 ticks, including per-mod attribution.
- **Operator: per-mod resource budget.** A mod can declare `max_cpu_us_per_tick = 800`; the profiler attributes per-tick CPU samples back to the mod's systems via tracing spans; mods exceeding budget emit `mod.cpu_quota_exceeded` and are demoted per M36D's quota policy.
- **Operator: auto-bisect on regression.** When a PR's gate fails by more than a configurable threshold (default 5%), the CI workflow bisects the merge-base..head range against the failing benchmark to identify the introducing commit and posts the SHA + diff link in the PR comment.
- **Indirectly-player-observable: no perceptible regression ships.** Every commit landing on `main` has passed the per-platform p99 gate on the supported reference hardware; players on each tier see the same per-tick wall time over time, not a slow drift toward stutter.
- **Indirectly-player-observable: pathological mod gets named.** A mod whose `update_world` system spikes p99 to 12 ms is identifiable by name in the player's logs + the server admin's audit, not as a vague "the game is slow today" complaint.

## Acceptance criteria

```gherkin
Scenario: cf-bench runs every subsystem on every supported platform
  Given a clean checkout of main on a Workstation / Apple Silicon / Linux VPS / Apple Mini Lab
  When `cargo bench -p cf-bench --all` runs
  Then every subsystem benchmark listed in cf-bench-reference.ron executes
  And produces a JSON result `target/cf-bench/results/<platform>/<subsystem>.json` with p50/p95/p99/max samples ≥ 1000 iterations
  And exit code is 0 if every subsystem passed its p99 gate, non-zero otherwise

Scenario: PR gate fails on p99 regression
  Given a PR that introduces a 25% slowdown in cf-material::kernel_ca
  When `m36g_bench_pr_gate.sh` runs against PR head
  Then the regression_gate verdict for cf-material is FAIL with regressed_pct=25.0
  And the workflow comment on the PR reads "REGRESSION: cf-material::kernel_ca p99 1.81 ms (baseline 1.45 ms, +24.8%) on Workstation"
  And the workflow exit code is non-zero
  And the PR cannot be merged until either the regression is fixed OR the baseline is updated via [baseline-update] PR

Scenario: Auto-bisect names the offending commit
  Given a PR whose merge-base..head range contains 7 commits
  And the PR gate detects a regression in cf-physics::narrowphase
  When `m36g_auto_bisect.sh cf-physics::narrowphase` runs
  Then git bisect drives the cf-bench harness across the range with binary-search
  And within max_iterations=8 it identifies the introducing commit SHA
  And the PR comment is updated: "Bisected to commit <sha> by <author>; diff: <link>"
  And total wall clock is under 20 minutes for a 7-commit range on Workstation

Scenario: Frame-time profiler captures per-system timeline
  Given a running cf-app instance with `cf-profile::frame_timeline` enabled
  When the operator runs `cfctl observe.perf.frame_timeline --ticks 60`
  Then the JSON response lists every system that ran during the last 60 ticks
  And each system entry has (system_name, tick, start_us, end_us, slice_us, mod_id_if_any)
  And system slices sum within 1% of the recorded whole-tick wall time

Scenario: Per-mod CPU accounting attributes spike to source mod
  Given a mod "fancy_smoke" whose `simulate_smoke` system spikes to 4 ms p99
  And the mod manifest declares `max_cpu_us_per_tick = 1500`
  When the profiler samples 60 consecutive ticks
  Then mod_cpu_quota_exceeded fires with mod_id="fancy_smoke" consumed_us=4000 budget_us=1500 tick=<n>
  And the operator's `cfctl observe.perf.subsystem_percentiles --by-mod` lists "fancy_smoke" as the top CPU consumer
  And per M36D mod_quota policy the mod is demoted / killed per server.ron policy

Scenario: Dashboard renders rolling per-subsystem percentiles
  Given 30 days of cf-bench runs on main are stored in the bench result archive
  When `cf-tools bench-dashboard --subsystem cf-atmos --window 30d --platform "Apple Silicon"` runs
  Then an HTML page is produced with three trend charts (p50, p95, p99) over 30 days
  And each PR merge to main is annotated as a vertical line on the chart with PR title + SHA tooltip
  And the rendering completes in under 5 seconds for 30 days of samples

Scenario: Headless servers skip render + audio benchmarks gracefully
  Given a Linux VPS reference platform (no GPU, headless)
  When cf-bench enumerates scenarios for this platform
  Then cf-render-2d::dispatch and cf-audio::mix benchmarks are SKIPPED with reason="headless_platform"
  And no other benchmark is skipped
  And the regression_gate verdict treats skipped scenarios as N/A (not FAIL)

Scenario: Cross-platform baseline drift detected
  Given a benchmark run on all four reference platforms
  When one platform's p99 has drifted ≥ 10% from its locked baseline without a corresponding [baseline-update] commit
  Then bench_regression_detected fires with platform=<name> subsystem=<name> drift_pct=<n>
  And the dashboard surfaces a red "BASELINE DRIFT" banner on the platform tab
  And a `m36g_drift_alert` GitHub issue is auto-opened

Scenario: Determinism — benchmark fixture reproducible across runs
  Given a benchmark scenario fixture with locked seed=0x0CF11_AAAA
  When `cargo bench -p cf-bench --bench material_ca -- --save-baseline run1` runs twice
  Then sim_checksum at the final tick of each run is byte-identical
  And per-iteration sample variance ≤ 2% on the same machine
  And bench results are NOT polluted by `Instant::now()` jitter in the scenario itself (timing is wrapped outside the sim run)

Scenario: Baseline update requires explicit tag
  Given a PR that silently raises an entry in cf-bench-reference.ron without `[baseline-update]` in the PR title
  When the PR gate runs
  Then the gate FAILS with reason="baseline_changed_without_tag"
  And the PR comment instructs: "Update titled [baseline-update]: cf-material p99 1.20 ms → 1.42 ms requires an explicit baseline update PR with sign-off"
  And the file diff is rejected

Scenario: cf-bench integrates with M36D's GPU/CPU parity matrix
  Given an existing cf-bench::gpu_cpu_parity_matrix scenario from M36D
  When cf-bench --all runs
  Then the parity matrix scenario participates as a regular bench entry with its own p50/p95/p99 entries
  And M36D's parity invariant (CPU output == GPU output) remains enforced as a separate check
  And no double-counting: parity_matrix shows up exactly once in the dashboard subsystem list

Scenario: Per-PR gate runtime stays under CI budget
  Given the full cf-bench suite on Workstation
  When `m36g_bench_pr_gate.sh --quick` runs (1000 iterations per subsystem, no flamegraph capture)
  Then total wall clock is under 8 minutes
  And the `--full` mode (10000 iterations + flamegraph capture) completes within 30 minutes on main-merge runs
  And both modes write structured JSON to `target/cf-bench/results/`
```

## Out of scope

- New optimization techniques (DR-054 owns the optimization stack; M36G measures it).
- Per-mod GPU quota (owned by M36D; M36G consumes the spans + accounts CPU side only).
- Player-facing performance HUD (cf-tools dashboard is operator-side; in-game perf overlay is owned separately by M48A polish + future debug overlay milestone).
- Cross-shard performance correlation (owned by M36E shard mesh).
- Anti-cheat performance fingerprinting (separate concern; bench fixtures are NOT a cheat-detection surface).
- Steam Deck per-tier perf gates (owned by M48A Steam Deck Verified gate; cf-bench may share fixtures but Deck-specific budgets ship with M48A).

## Notes for the implementer

- `cf-bench` already exists per M36D's `gpu_cpu_parity_matrix.rs` reservation; this spec extends it, does NOT duplicate it.
- Every benchmark MUST use a locked seed + locked scenario fixture; non-deterministic input destroys the regression gate.
- Wall-clock timing wraps the harness, NOT the inner sim — use `Instant::now()` outside the sim loop, never inside (the determinism rule still applies to sim crates).
- `cf-bench-reference.ron` is the single source of truth for baselines; CI gate diffs PR head against this file's locked values, not against last-merge's runtime samples (avoids drift compounding).
- `auto_bisect.rs` shells out to `git bisect` with a custom `--exec`; the harness must produce a single boolean (`pass` / `fail`) per commit candidate.
- Per-mod CPU attribution uses `tracing::span!` with `mod_id` as a span field; M36D's GPU quota framework already does the GPU-side; this is the CPU twin.
- HTML dashboard generation must be deterministic for the same input JSON (no timestamps in DOM output) so dashboard regen is idempotent.
- Frame-time profiler uses a ring buffer of last N ticks (default 600); per-system spans are stored as `(u16 system_id, u32 start_us, u32 end_us)` to keep memory bounded.
- Auto-bisect MUST refuse to bisect across a known-bad merge commit; the manifest declares quarantined ranges.
- Reference numbers locked in this spec are starting estimates derived from DR-054 + M36C tier budgets; the implementer's first PR after harness lands is expected to be a `[baseline-update]` calibration commit that anchors the numbers to actual measured medians.
- CI workflow `m36g_perf_gate.yml` runs ONLY on Workstation reference hardware for per-PR speed; Apple Silicon + Linux VPS + Apple Mini Lab reference runs land on the nightly schedule and write to the dashboard archive.
- `cf-tools bench-dashboard` is invocable both as a CLI binary AND via cfctl admin route `admin.bench.publish_dashboard`; operators can refresh on demand.
