# M41B — Mod Hash Sync + Server Authority + Lobby Discovery + Cross-Region Latency Compensation

## Status

`active`

## Intent

M41B locks the **online-match join contract + cross-region playability layer** that M41 declared but did not exhaust: per-mod blake3 content hashes compared at session join with deterministic mismatch surfacing, automatic mod download from the server when a client is missing or stale (gated by the M36 trust-tier ladder), authoritative-server message ordering rules that fix the per-tick + cross-actor + cross-shard event sequence beyond a doubt, a lobby browser with region-filter + ping-bucket + mod-compat + tier filters, cross-region MMR balancing that adjusts matchmaking weighting by RTT class, and a spectator-tier latency-tolerance profile that lets observers watch a match from 400+ ms away without rollback-storm artifacts. M41 ships online co-op with self-hosted servers; M41B fills the join-time + cross-region + spectate gaps that block scale.

## Player-facing behavior

- **Mod-mismatch join is informative, not cryptic.** Player joining a server with mod `radio_overhaul@1.2.3` they do not have locally sees a dialog: "Server requires `radio_overhaul` v1.2.3 (community-tier, 2.1 MB). Download?" with Download / Skip-and-disconnect buttons. Verified-tier mods auto-download silently with a progress toast.
- **Mod-mismatch with a malicious or unsigned mod is blocked.** Player joining a server with mod `evil_aimbot@0.0.1` (no signature, not on the trust list) sees: "Server uses an unverified mod that cannot be auto-downloaded. Contact the host." No silent download from an untrusted source ever happens.
- **Lobby browser feels alive.** Server list refreshes within 2 seconds of opening the browser; ping shows as a single integer + color-coded bucket (≤50 / 50-100 / 100-200 / 200+ ms); region-filter chips toggle on click; mod-compat chip turns red if the player is missing required mods.
- **Code-based private join works regardless of region.** 6-character private codes resolve via the lobby directory to a server endpoint + relay candidate in under 1 second.
- **Cross-region matches are playable.** A player in EU connects to a NA dedicated server at 130 ms RTT and the match feels responsive thanks to prediction + bigger rollback budget on cross-region sessions. Player sees `region: NA-EAST · rtt: 130 ms` in the session HUD.
- **Cross-region MMR balancing avoids unfair fights.** A 1500-MMR player in EU does not get matched against a 1500-MMR player in NA-EAST as if they were the same; the matcher accounts for the 130-ms-RTT disadvantage with an MMR-equivalent of about 50 points, weighted toward the disadvantaged side.
- **Spectators don't break the game.** A spectator at 400 ms RTT watching a match doesn't trigger rollback storms or input thrash on the authoritative server, because spectator sessions use a tolerant-latency profile: bigger snapshot interval, no input upload, prediction disabled.
- **Authoritative ordering is reproducible.** Two replays of the same match by two different spectators end up byte-identical; cross-shard events are ordered by `(global_tick, shard_id, seq)` not arrival time.

## Acceptance criteria

```gherkin
Scenario: Per-mod blake3 hash is deterministic across OS
  Given the mod package "radio_overhaul" with 12 files at version 1.2.3
  When `cf-mod hash radio_overhaul` is run on Linux, macOS, and Windows
  Then all three computed per-mod blake3 hashes are byte-identical
  And the per-file blake3 list is byte-identical
  And the CI gate fails any patch that introduces hash divergence across OS

Scenario: Mod hash mismatch at join surfaces an actionable dialog
  Given a server requiring "radio_overhaul" v1.2.3 (community-tier, 2.1 MB)
  And a client lacking the mod entirely
  When the client sends Handshake with its current mod hash set
  Then the server responds with ModHashMismatch { mod: "radio_overhaul", required: "<blake3>", offered: null, tier: "community", size_bytes: 2208256 }
  And the client UI shows: "Server requires `radio_overhaul` v1.2.3 (community-tier, 2.1 MB). Download?"
  And no auto-download begins without the player's consent

Scenario: Verified-tier mod auto-downloads with a progress toast
  Given a server requiring "official_radio_pack" v2.0.0 (verified-tier, signed by Madreag)
  And a client lacking the mod
  When the client sends Handshake with its current mod hash set
  Then the server begins the streaming auto-download over the reliable QUIC stream "mod_blob"
  And the client UI shows a progress toast: "Downloading official_radio_pack (verified)... 0% → 100%"
  And on completion the client recomputes the blake3 and matches the server's expected hash before loading the mod
  And the client joins the session without re-handshaking

Scenario: Untrusted-mod auto-download is refused
  Given a server requiring "evil_aimbot" v0.0.1 (no signature, not on the verified-tier list)
  And a client with strict trust profile
  When the server attempts to push the mod blob
  Then the client refuses the download
  And the UI shows: "Server uses an unverified mod that cannot be auto-downloaded. Contact the host."
  And the session is closed with no mod loaded

Scenario: Authoritative ordering is reproducible across spectators
  Given a 4-player match running on cf-server --mode coop_room
  And two spectators recording per-spectator replay bundles
  When the match runs for 5 minutes producing 18,000 ticks of events
  Then the two spectator replay bundles compare byte-identical via `cf-headless replay-compare`
  And every event carries `(global_tick, shard_id, seq)` and is sorted by that tuple in both bundles
  And no event arrival-order tiebreak is observable in the bundles

Scenario: Lobby browser filters by region + ping + mod compat + tier
  Given the lobby directory holds 240 registered servers across 6 regions
  When the player opens the lobby browser and selects "EU-WEST" + "ping ≤ 100 ms" + "mod-compat with my install" + "trust tier ≥ verified"
  Then the visible result list shrinks deterministically to the matching subset within 200 ms
  And every visible row's ping bucket color matches the player's measured RTT
  And the mod-compat indicator turns green if the player has every required mod, yellow if download is needed, red if a required mod is untrusted-tier

Scenario: Private 6-character code resolves to a session
  Given a server registered with the lobby directory and configured for private joins
  And a 6-character invite code "K7M-4ZP" that maps to a session endpoint
  When a friend types "K7M-4ZP" in the join dialog
  Then the lobby directory resolves the code to the server endpoint + relay candidate in under 1 second
  And the join handshake proceeds normally including the M41B mod-hash exchange

Scenario: Cross-region MMR balancer applies a region penalty
  Given a 1500-MMR player in EU-WEST
  And a candidate 1500-MMR opponent in NA-EAST at expected 130 ms RTT
  When the matcher evaluates the pair
  Then the matcher applies an effective +50 MMR to the disadvantaged side
  And the match is permitted only if the resulting balance is within the per-mode tolerance window
  And the match.region_balanced event records { eu_west_mmr: 1500, na_east_mmr: 1550_effective, rtt_class: "100_200_ms" }

Scenario: Cross-region match feels responsive at 130 ms RTT
  Given a player at 130 ms RTT to the dedicated server
  When the player issues an input "move right"
  Then the player's local actor begins moving within 1 frame (prediction)
  And the authoritative confirm arrives within ~130 ms
  And no snap-back is observable when the prediction matches the server's resolved input

Scenario: Spectator at 400 ms RTT does not cause a rollback storm
  Given an authoritative match in progress
  And a spectator joining with the latency-tolerant spectator profile from spectator_profile.ron
  When the spectator's session runs for 60 seconds at 400 ms RTT
  Then the spectator's snapshot interval is 6 ticks (not 1)
  And the spectator never uploads input
  And the spectator never triggers rollback on the authoritative server
  And the spectator HUD shows "watching as spectator · latency-tolerant"

Scenario: Mod auto-download rejected when blob blake3 mismatches expected

  When the client recomputes the post-download blake3

  And the client deletes the partial download
  And emits mod.download_rejected { reason: "blake3_mismatch", mod: "radio_overhaul" }
  And the session is closed

Scenario: Lobby refresh stays under 2 seconds with 240 registered servers
  Given a populated lobby directory with 240 servers
  When the player presses the "refresh" button in the lobby browser
  Then the new server list is rendered within 2 seconds at p95
  And ping is sampled in parallel using QUIC PING frames, not full handshakes
```

## Notes for the implementer

- Per-mod blake3 hash MUST be computed over a sorted-by-path file list with canonicalized line endings (LF only) + canonicalized JSON whitespace (compact, sorted keys). Anything else and the cross-OS determinism gate fails — a mod authored on Windows will hash differently from the same files on Linux.
- Trust-tier ladder is the canonical gate. Order, low → high: `experimental < community < verified < vanilla`. Strict-trust clients refuse auto-download below `verified`. Match this exactly to the M36 ladder; do not invent a new ordering.
- Auto-download streams the mod blob over a QUIC reliable bidirectional stream named "mod_blob"; the M8B reliable stream naming convention applies. The size of a single mod blob is capped at 64 MB by default (`net.mod_blob.max_bytes`); larger mods require manual install.
- Lobby refresh MUST use QUIC PING frames for ping sampling, not full session handshakes. Full handshakes are 8+ roundtrips with TLS + mod hash check; the lobby browser would feel sluggish.
- Region penalty table is a tunable in `content/net/region_penalty.ron` with the canonical M38 7-tier hierarchy. Default values: within-region 0, adjacent-region (≤50 ms class) +20 MMR, distant-region (50-200 ms class) +50 MMR, far-region (200+ ms class) +100 MMR.
- Cross-region MMR balancing is opt-in per mode. Casual coop matches off; competitive PvP arenas on. The matcher reads `match_mode_config.cross_region_balance: bool` from the per-mode RON.
- Spectator profile MUST be a single RON file `content/net/spectator_profile.ron` so operators can tune it without a recompile. Default: `snapshot_interval_ticks: 6`, `predict_inputs: false`, `upload_inputs: false`, `rollback_enabled: false`.
- Authoritative ordering tuple is canonical: `(global_tick, shard_id, seq)`. `seq` is a per-shard u32 that resets at every checkpoint epoch (M36E). Cross-shard merge uses the M36E broadcast bus.
- All new schemas MUST be added to `dump_schemas --check` so schema drift fails CI.
- All new events have `cosmetic: false`. Mod-hash + match-region + spectator events are sim-relevant + non-droppable.
- Audit log MUST record source-IP-hash (BLAKE3 of `source_ip || daily_pepper`), never raw IP. The lobby directory's pepper rotates daily. This is the same privacy posture as M36B telemetry.
- The lobby directory's private-code resolver MUST rate-limit per source IP at 30 lookups per minute. Brute-forcing a 6-char code is otherwise feasible at scale.
- Do NOT trust the client's self-reported region. Region classification is server-derived from connection IP geolocation (via the M36 `cf-server-ops` IP→region map); clients see their region but cannot set it.
- The mod auto-download flow MUST validate the post-download blake3 against the server-advertised hash BEFORE the mod is loaded. A blob that survives transport corruption + matches expected length but mismatches blake3 must be deleted, not loaded.
- Per the M36 anti-cheat ladder: in `competitive` profile, any mod_hash_mismatch outcome that is not auto-resolved closes the session. No "play without the mod and hope for the best" fallback.
- Per the M42 self-hosted deployment story: hosts that do not run a TURN relay still work because M8B's ICE-lite is parallel + STUN is enough for the majority of NAT-pairs. The TURN relay is the long-tail safety net.
