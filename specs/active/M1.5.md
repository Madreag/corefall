# M1.5 — Micro Breach Fun Slice

## Status

`active`

## Intent

One 60-90 second playable scenario — `micro_breach` — that proves the M1 actor controller is fun to use under pressure: spawn → breach a soft barrier → fight or bypass one reactive enemy → reach extraction. Wins and losses both happen, both produce honest run bundles, and a scripted cfctl replay can drive both paths without human input.

## Player-facing behavior

- Player spawns at one end of a small map. An objective banner says "Breach the wall and reach the extraction zone."
- A soft destructible strip blocks the path. The digger tool carves through it; refusal labels appear if the wrong tool is used.
- One reactive enemy guard patrols near the breach. It has limited sight cone, slow aim, imperfect fire, finite HP.
- The player must either kill the guard or sneak past, then reach the extraction zone within 90 seconds.
- HUD shows: objective text, time remaining, player HP, enemy status, selected item, last important event.
- Win = reach extraction with player alive. Lose = player dies OR timer expires OR objective failed.
- Both outcomes emit a structured `mission.mission_resolved` event with reason.

## Acceptance criteria

```gherkin
Scenario: Win path drives end-to-end via cfctl
  Given a fresh micro_breach scenario
  When the cfctl script micro_breach_win.cfctl.json runs
  Then the player reaches the extraction zone within 90 seconds
  And mission.mission_resolved fires with result=won
  And the cf-e2e --expect mission.result=won assertion passes
  And the run bundle validates

Scenario: Loss path drives end-to-end via cfctl
  Given a fresh micro_breach scenario
  When the cfctl script micro_breach_loss.cfctl.json runs
  Then the player dies OR the 90s timer expires OR the objective fails
  And mission.mission_resolved fires with result=lost
  And mission.loss_reason carries a label from the typed LossReason enum
  And the cf-e2e --expect mission.result=lost assertion passes

Scenario: Reactive enemy emits perception/state/tactic events
  Given a ReactiveGuard in the scenario
  When the player enters its sight cone
  Then ai.ai_perception fires with saw_player=true
  And ai.state_changed fires with from=Idle, to=Alert (then later to=Engaged when firing)
  And ai.tactic_chosen fires with reason from a documented vocabulary
  When the guard fires and misses
  Then ai.missed_shot_reason fires with a reason label

Scenario: Soft breach emits terrain-compatible events
  Given a BreachStrip blocking the path
  When the player digs through it
  Then terrain.terrain_carved events fire with bbox + material id + count
  And the events have the same shape M2 chunked terrain will emit
  And replay consumers do not need to change when M2 lands

Scenario: Digger refusal has a reason label
  Given a metal-nohook tile
  When the player attempts to dig it
  Then tool_refused fires with reason="material_not_diggable"
  And the actor's HUD last-event line shows "REFUSED: cannot dig metal"

Scenario: Objective state transitions fire events
  Given the scenario starts
  Then mission.objective_started fires for the breach objective
  When the breach succeeds
  Then mission.objective_completed fires with the objective id
  When the player reaches extraction
  Then mission.objective_completed fires for "reach extraction"
  And mission.mission_resolved fires with result=won

Scenario: HUD readability
  Given the scenario is running
  Then the HUD shows objective text
  And a count-down timer
  And player HP
  And enemy HP (when in sight)
  And the last important event ticker

Scenario: Mission state has analytics fields
  Given a running mission
  Then MissionState carries started_at_tick (set on first tick)
  And last_transition_tick (updated on every state change)
  And loss_reason_label (set when result=lost)
```

## Out of scope

- Multiple enemies — M5+ scenarios
- Squad/group AI — DR-008 deeper
- Comic-noir mission card — M4B (deferred)
- Mobility/Hazard/Repair test lanes — M2/M2.5/M5 follow-on
- Real chunked terrain — M2 (BreachStrip is a stand-in; events are forward-compatible)
- Enemy weapon drops — DR-018 / M5 death meaning ladder
- Death sprite / corpse persistence — M5

## Dependencies

- M1 actor controller (must be done): act.player.* methods, body status state machine, HUD ammo/status.

## Notes for the implementer

- ReactiveGuard's "intent" does NOT flow through ControlIntent — it uses a separate EnemyTickReport. This is by design (player intent and AI intent have different shapes).
- BreachStrip events MUST be forward-compatible with M2's chunked terrain (`terrain.terrain_carved` schema). M2 will replace the BreachStrip implementation behind the same event surface.
- LossReason is a typed enum with `as_str()` — do NOT use string literals for new reasons.
- The 60-90 second window is real. If the scenario routinely runs over 90s, the script is too long; cut it.
- Project-owner playtest survey is OPTIONAL; AI Self-Test (the scripted win + loss + observability proof) is the primary gate.
