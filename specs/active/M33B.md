# M33B — Lua Sandbox API Surface + Hot-Reload + Per-Callback Permissions + Modder Documentation

## Status

`active`

## Intent

**M33B is the Lua sandbox deep-dive milestone** — closes the surface-level Lua mention in M33 with a full API surface (10 canonical callbacks + per-callback capability table + forbidden-API list + sandboxed standard library + deterministic runtime) + hot-reload safety + Lua-table-to-Rust-struct marshalling layer + an auto-generated modder API documentation site. After M33B, a modder can write a per-weapon `OnFire` callback in Lua, hot-reload it during play, see syntax + capability errors before the script runs, and read full API docs generated from the same source-of-truth as the engine bindings.

M33B promise: **"Lua scripting is a first-class extension surface — every callback is sandboxed, every API is documented, every script hot-reloads in <100 ms, and a malicious script cannot escape the sandbox, mutate save data, call the network, or break replay determinism."**

## Player-facing behavior

### 10 canonical Lua callbacks (M33 reservation deepened)

Every Lua mod registers callbacks against a fixed set of named hooks. Engine fires each at the documented sim site; un-registered hooks are skipped at zero cost.

| Callback | Signature | Sim site | Determinism class | Default capability tier |
|---|---|---|---|---|
| `OnUpdate(actor, dt)` | per-tick per-actor | end-of-actor-tick | sim-affecting | `sim_read_write` |
| `OnFire(weapon, target_hint)` | weapon discharge | post-discharge, pre-projectile-spawn | sim-affecting | `sim_read_write` |
| `OnUse(actor, item)` | item use action | post-cfctl `act.player.use_item` | sim-affecting | `sim_read_write` |
| `OnDeath(actor, cause)` | actor death | post-knockdown-to-corpse | sim-affecting | `sim_read_write` |
| `OnHit(projectile, target, damage)` | projectile-vs-actor / projectile-vs-tile | post-impact, pre-damage-apply | sim-affecting | `sim_read_write` |
| `OnSpawn(entity)` | actor / device / item spawn | post-instantiation, pre-first-tick | sim-affecting | `sim_read_write` |
| `OnTick(world, tick)` | per-world per-tick | end-of-world-tick | sim-affecting | `sim_read` |
| `OnReload(weapon, mag_state)` | weapon reload | post-mag-swap, pre-availability | sim-affecting | `sim_read_write` |
| `OnCraft(actor, recipe, output)` | crafting recipe completion | post-craft, pre-inventory-insert | sim-affecting | `sim_read_write` |
| `OnTransition(scenario_from, scenario_to)` | scenario boundary | post-scenario-close, pre-next-load | session-only | `session_read` |

Each callback returns either `nil` (engine continues) or a typed result table (engine merges / overrides per callback contract). Return-shape mismatch is a recoverable error; offending script disabled, event fired, sim continues.

### Per-callback permission table

Every mod manifest declares per-callback capability requests. Engine refuses to load a mod whose declared capabilities exceed its trust tier (see M33C for the trust-tier kernel).

```ron
// in mod.manifest.ron
callbacks: {
    "OnFire": { capabilities: ["sim_read", "sim_write", "event_emit"] },
    "OnUpdate": { capabilities: ["sim_read"] },
    "OnDeath": { capabilities: ["sim_read", "event_emit"] },
}
```

Capability grammar (5 tiers, additive):

| Capability | Grants | Forbidden APIs gated by absence |
|---|---|---|
| `sim_read` | Query world / actor / weapon / material state | mutators below |
| `sim_write` | Mutate actor state, spawn entities, apply damage | `entity_spawn`, `actor_apply_damage`, `world_set_tile` |
| `event_emit` | Push a structured `mod.*` event into the replay stream | `replay_emit` |
| `session_read` | Read non-sim session state (scenario id, player profile id) | `session_get`, `profile_get` |
| `ui_overlay` | Draw a HUD overlay (M33 HUD editor mods only) | `hud_draw_text`, `hud_draw_rect` |

Capabilities NEVER granted to any tier (hard-coded refusal at load time):

- File I/O of any kind (`io.*`, `dofile`, `loadfile`)
- Network of any kind (`socket.*`, `http.*`, `tcp.*`, `udp.*`)
- Process control (`os.execute`, `os.exit`, `os.remove`, `os.rename`)
- Shell escape (`io.popen`, backticks, `posix.*`)
- Native library load (`require` of any `.so` / `.dll` / `.dylib`)
- Time-of-day clocks (`os.time`, `os.date`, `os.clock`) — replaced by deterministic `cf.tick()` / `cf.rng()`
- Reflection that escapes the sandbox (`debug.getregistry`, `debug.setmetatable` on engine tables)
- Garbage-collector knobs (`collectgarbage("setpause", …)`) that would break per-tick budget

### Sandboxed standard library

Engine ships `cf-script-sandbox` — a curated `_ENV` that exposes:

- Pure functions: `math.*` (no `math.random` — use `cf.rng()`), `string.*`, `table.*`, `bit32.*`
- `cf.tick()` — deterministic monotonic tick counter
- `cf.rng(stream_id) -> u64` — seeded RNG channel per M14 deterministic-RNG rules
- `cf.log(level, msg)` — routes to `tracing` at `info`/`warn`/`error`; rate-limited per mod
- `cf.event(name, payload)` — emit `mod.<mod_id>.<name>` into replay (requires `event_emit`)
- `cf.entity_*`, `cf.actor_*`, `cf.weapon_*`, `cf.world_*` — typed query/mutate per capability gate

`require` is rebound to a whitelist over `<mod>/lua/` files only. Cyclic require detected + refused. Per-script LoC cap is 50 000 to bound JIT warmup; warning at 25 000.

### Lua-table-to-Rust-struct marshalling layer (`cf-script-marshal`)

Engine ↔ script boundary uses a typed marshalling layer. For each engine struct exposed to Lua, the marshaller:

- Generates a Lua-side accessor table with read-only fields (`actor.id`, `actor.health`, `actor.position`)
- Mutators go through capability-gated functions (`cf.actor_set_health(actor, value)`) — never raw field writes
- NaN / Inf / out-of-range floats coerced or refused at the marshal boundary (per M14 sim invariants)
- Tables coming back into Rust validated via `serde::Deserialize` derive; offending shape returns typed error to script
- Marshalling is allocation-bounded: per-callback heap budget 64 KiB; OOM → script disabled + event

### Hot-reload safety

`act.player.script_reload { mod_id }` (cfctl method) triggers:

1. New script source parsed + lexed offline — syntax error → reject; cfctl returns error; running script untouched
2. New script's declared capabilities re-validated against trust tier — refusal → reject
3. Engine pauses sim for 1 tick (M14 deterministic pause)
4. Old `_ENV` torn down; per-mod state preserved via `cf.state` table (modder-managed)
5. New script loaded into fresh `_ENV`; per-callback registration re-bound
6. Engine resumes sim; `script.hot_reloaded { mod_id, sha256, ms }` event fires
7. If new script throws on first invocation, it is disabled + previous version automatically restored; `script.hot_reload_rollback` fires

Hot-reload is forbidden during multiplayer sessions unless all peers agree (M36 lobby vote). Single-player accepts unconditionally.

### Modder API documentation generator (`cargo run -p cf-mod -- docs`)

- Parses `cf-script-bindings` source for `#[lua_api]` annotations
- Emits HTML + Markdown to `target/mod-docs/`
- Per-API entry: name + signature + capability required + example + since-version + sim site + determinism class
- Generates callback reference (the 10 canonical hooks) with copy-paste skeletons
- Generates capability-tier table + forbidden-API list with refusal-error examples
- Generates marshalling type catalogue (Rust struct → Lua table shape)
- Search index + cross-reference links; output bundles into `.cfdocs` zip ready for upload to Workshop "Reference" tab

### Per-callback error reporting

When a callback throws or violates capability:

- Engine catches the panic at the FFI boundary; sim continues
- Mod's offending callback is disabled (other callbacks of same mod continue)
- `script.callback_error { mod_id, callback, line, message }` event fires
- Player notified via M11 banner: "Mod `<mod_name>`: OnFire disabled (line 42: capability `sim_write` not granted)"
- Re-enable via `act.player.script_reenable { mod_id, callback }` after edit + hot-reload

## Acceptance criteria

```gherkin
Scenario: All 10 canonical callbacks fire at their documented sim sites
  Given a test mod registering OnUpdate / OnFire / OnUse / OnDeath / OnHit / OnSpawn / OnTick / OnReload / OnCraft / OnTransition
  When a 600-tick scenario runs covering every site
  Then each callback fires exactly once per documented trigger
  And cf-replay records script.invoked { mod_id, callback, tick } for each
  And the invocation order matches the per-callback determinism class table

Scenario: A mod requesting sim_write without trust gets refused at load
  Given a mod with manifest declaring OnFire capability "sim_write"
  And the mod's trust tier is "untrusted" (read-only by default)
  When the engine attempts to load the mod
  Then script_capability_denied event fires with mod_id + callback + denied_capability
  And the mod is NOT registered; sim continues unaffected
  And the player is shown a banner: "Mod `<name>` declines: sim_write not granted by your trust setting"

Scenario: Forbidden APIs cannot be called even at the highest trust tier
  Given a verified-tier mod whose Lua source calls io.open("/etc/passwd", "w")
  When the script loads
  Then the sandbox refuses to bind io.open into the script's _ENV
  And evaluating io.open at runtime raises "attempt to call a nil value (global 'io')"
  And script_callback_error fires; the offending callback is disabled
  And no file under /etc is created

Scenario: Hot-reload swaps a callback in under 100 ms with sim continuity
  Given a running scenario with a mod that prints "v1" in OnFire
  When the player edits the script to print "v2" and invokes act.player.script_reload
  Then script_hot_reloaded fires with sha256 + duration_ms < 100
  And the engine pauses for exactly 1 tick during the swap
  And the next OnFire invocation logs "v2"
  And cf.state values set by v1 are visible to v2

Scenario: Hot-reload rollback when new script throws on first call
  Given a mod with a working v1 OnFire callback
  When the player hot-reloads to a v2 that throws on first invocation
  Then script_hot_reload_rollback fires
  And v1 is automatically re-installed
  And subsequent OnFire invocations execute v1 (not v2)
  And the in-editor error pane shows v2's line + message

Scenario: Per-tick CPU budget kills a runaway script
  Given a mod whose OnUpdate enters an infinite loop
  When the script executes
  Then the per-tick CPU budget (5 ms default) is exhausted
  And script_budget_exceeded fires with mod_id + callback + elapsed_us
  And the offending callback is disabled for the remainder of the session
  And the sim continues at the configured tick rate

Scenario: Marshalling rejects NaN / Inf from script into the sim
  Given a mod whose OnFire returns { damage_multiplier = 0/0 }  -- NaN
  When the engine consumes the return table via cf-script-marshal
  Then the marshaller refuses the value and substitutes the documented default (1.0)
  And script_callback_error fires with reason="nan_in_return"
  And no NaN reaches cf-projectile

Scenario: math.random and os.time are not available; cf.rng + cf.tick are
  Given a Lua script
  When the script evaluates math.random / os.time / os.clock
  Then each is nil (not bound into _ENV)
  When the script evaluates cf.rng(0) twice with the same scenario seed across two engines
  Then both engines yield identical 64-bit values
  And cf.tick() returns the same monotonic value on both engines

Scenario: API documentation generator emits a complete reference
  Given `cargo run -p cf-mod -- docs` from a clean repo
  When generation completes
  Then target/mod-docs/index.html exists
  And target/mod-docs/callbacks/onfire.md documents OnFire's signature, capability, sim site, determinism class, since-version
  And the forbidden-API table is present with refusal examples for io.open / os.execute / require("ffi")
  And target/mod-docs/cfdocs.zip is a valid archive uploadable as a Workshop "Reference" attachment

Scenario: Determinism across two engines with a Lua mod loaded
  Given m33b_lua_determinism_seeded.ron on two engines with the same seed and the same mod sha256
  When 1800 ticks elapse exercising OnFire / OnHit / OnCraft
  Then every script.* event matches in payload + order
  And SaveBlob.checksum at tick 1800 is identical on both engines

Scenario: Multiplayer hot-reload refused without peer vote
  Given a 4-player co-op session with a Lua mod loaded
  When one peer attempts act.player.script_reload without a vote
  Then the cfctl call returns error "hot_reload_requires_lobby_vote"
  And no swap occurs on any peer
  When the lobby votes 4/4 yes
  Then the swap proceeds and script_hot_reloaded fires on every peer at the same tick

Scenario: In-editor capability lint underlines violations before save
  Given the M33 in-game Lua editor open on a mod with capability=["sim_read"]
  When the modder types `cf.actor_set_health(actor, 99)` (requires sim_write)
  Then a red squiggle appears under the call
  And the hover tooltip reads: "Capability `sim_write` not granted by mod manifest; raise tier or remove call"
  And the save action is disabled until either the manifest or the line is amended
```

## Out of scope

- Lua source-level static type system / type inference — Lua stays dynamically typed; capability + marshalling is the contract.
- JIT tuning knobs exposed to modders — engine selects between Lua 5.4 interpreter and LuaJIT per build; modders see one runtime.
- IC10 chip programming (separate language; M29A + M33D scope) — M33B is Lua only.
- Visual scripting / node graph alternative to Lua — DR-006 considered + rejected (option C); not in scope.
- Per-callback async / coroutine yielding across ticks — Lua coroutines work within a single tick only.
- DLC-style closed-source script encryption — modding is open by design (DR-006).

## Dependencies

- **M33 (mod workbench surface)** must close OR concurrent — provides editor pane + manifest discovery
- **M14 deterministic RNG (active)** — `cf.rng()` seeds off M14's per-stream channels

## Notes for the implementer

- **cfctl write-merge convention** — multiple specs each add ~5 cfctl methods to `cf-control/src/server.rs`; to avoid merge conflicts and tangled handlers, **M33B creates `game/crates/cf-control/src/m33b_actions.rs`** containing the `script_reload`, `script_reenable`, and `observe.mod.scripts` handlers and registers from `cf-control/src/server.rs` via a `pub mod m33b_actions;` line plus a single `m33b_actions::register(&mut router)` call. `server.rs` itself stays a thin dispatcher; per-spec handler bodies live in their own files. Same pattern is mirrored by M33C / M33D / M37C.
- Pin `mlua = "0.10"` with feature `lua54`; do NOT enable `unsafe-send` (sim crates are single-threaded).
- Per-mod isolate uses a separate `Lua` instance; no shared globals between mods (a mod cannot see another mod's `cf.state`).
- The `#[lua_api]` proc-macro auto-emits both the binding and the doc entry — single source of truth. Modify the macro to add a new API; never hand-write a binding.
- Per-tick CPU budget is wall-clock; do not use Lua instruction counting (LuaJIT skews counts).
- Hot-reload pause MUST go through `cf-sim-core::pause(1)` so save / replay determinism survives.
- Forbidden-API list lives in `cf-script-sandbox/src/forbidden.rs` as a constant; add a row + a regression test when discovering a new escape (e.g., `package.loadlib`).
- `cf.event` payload size capped at 4 KiB; oversize → error, payload dropped, event still fires with `truncated=true`.
- The capability lint in the in-game editor reuses the same `forbidden.rs` table — never branch the implementation.
