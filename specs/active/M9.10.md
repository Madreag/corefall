# M9.10 — Comprehensive Server Config + Admin CLI + Settings Hierarchy

## Status

`active`

## Intent

**M9.10 is the comprehensive configuration architecture milestone** — the canonical contract for HOW Corefall is configured across every layer: engine defaults → system config → profile config → scenario config → server config → CLI args → runtime cfctl edits. After M9.10, server admins can edit a single `server.ron` file to tune every gameplay mechanic, every player has a `profile.ron` for personal preferences, and the CLI surface is **fully controllable by server admin from cfctl** (including locking specific keys against client override).

Per the user's vision: **"I want most things to be configurable via CLI and/or settings files for customizability and tuning... like server settings file you can edit and personal settings file you can edit, and CLI should be controllable by server admin etc."**

M9.10 promise: **"every dial in the game is a settings key; every settings key has a typed schema; every key can be locked by server admin to prevent client override; the same config file format works for solo, LAN, online, and MMO."**

## Player-facing behavior

### 7-tier settings hierarchy (lowest → highest priority)

Per the user demand: **"server settings file you can edit and personal settings file you can edit, and CLI should be controllable by server admin."**

Settings cascade from lowest to highest priority. Each tier can lock keys against override from any lower tier.

| # | Tier | File / Source | Locked-by | Player-editable | Override scope |
|---|---|---|---|---|---|
| 1 | **Engine defaults** | Compiled-in code (Rust constants) | Build (immutable) | NO | Universal fallback |
| 2 | **System config** | `~/.config/corefall/system.ron` | System admin (Linux: root; macOS/Windows: per-user) | YES (admin only) | Per-machine OS defaults |
| 3 | **Profile config** | `~/.config/corefall/profile.ron` | Profile owner | YES | Per-user gameplay preferences |
| 4 | **Scenario config** | In scenario manifest (`scenario.ron`) | Scenario author | NO (player) | Per-mission overrides |
| 5 | **Server config** | `<server-dir>/server.ron` | Server admin | NO (player) | Online/MMO session overrides |
| 6 | **Session config** | CLI args (`--key=value`) | Session launcher | NO (player) | One-time session overrides |
| 7 | **Runtime cfctl** | `act.settings.set` JSON-RPC | Server admin (locked keys) OR player (unlocked keys) | YES | Live in-session edits |

**Key locking semantics:**

Each tier can declare a key as `locked` to prevent override by higher tiers:

```ron
// server.ron
ServerConfig (
    // Server admin locks tick rate to 60 Hz; no client override allowed
    tick_rate_hz: (value: 60, locked_by: "server", reason: "Anti-cheat: prevent client framerate tampering"),

    // Server admin sets default difficulty but allows player override
    ai_difficulty: (value: "tough_crowd", locked: false),

    // Server admin locks anti-cheat profile to competitive
    anti_cheat_profile: (value: "competitive", locked_by: "server", reason: "PvP rules"),

    // Settings player can edit:
    sound_volume_default: (value: 0.8, locked: false),
)
```

When a lower tier tries to override a locked key, the engine rejects the change with structured event:

```json
{
  "type": "settings.override_rejected",
  "key": "tick_rate_hz",
  "attempted_value": 120,
  "locked_by_tier": "server",
  "reason": "Anti-cheat: prevent client framerate tampering",
  "actor_id": "player_42"
}
```

### CLI commands — server admin remote control

Per M9 + DR-052, the cfctl CLI accepts admin commands locked to server admin:

```bash
# Admin login
cfctl admin login --server <addr:port> --admin-token <secret>

# Read current server config
cfctl admin observe.server.config

# Set a single key
cfctl admin set raid_frequency_multiplier 2.0

# Lock a key against player override
cfctl admin lock anti_cheat_profile

# Unlock a key (allow player override)
cfctl admin unlock damage_numbers

# Hot-reload server config from disk
cfctl admin reload-config

# Kick player
cfctl admin kick <player_id> [--reason <text>] [--duration <minutes>]

# Ban player (permanent)
cfctl admin ban <player_id> --reason <text>

# Save manually
cfctl admin save <slot_name>

# Restart server gracefully
cfctl admin restart

# Hot-load a different scenario
cfctl admin hot-load <scenario_id>

# Manage mods
cfctl admin mod whitelist add <mod_id>
cfctl admin mod whitelist remove <mod_id>
cfctl admin mod hash sync --strict

# Inspect player
cfctl admin inspect player <player_id>

# Mass commands (apply to all players)
cfctl admin broadcast "Server restart in 5 minutes"

# Read server logs
cfctl admin observe.server.logs --follow

# Cheater alerts
cfctl admin observe.admin.alerts --json
```

### Deep simulation — full schema + UI generation + audit trail

The full schema lives at `docs/plan/spec/settings-schema.ron` and is the single source of truth. **200+ launch keys** spanning: engine (8) + HUD/accessibility (20) + audio (10) + controls (15) + power (18) + crafting (12) + AI (10) + damage (12) + survival (15) + server (25) + atmospherics (8) + hazards (6) + materials (5) + chassis (10) + mod (8) + replay (5) + advanced (18).

**Each key has typed schema:** `name`, `type`, `default`, `valid_range`, `units`, `description`, `owner`, `lockable_by` (which tiers can lock), `requires_restart`, `ui_tab`, `ui_widget` (Slider / NumberInput / DropDown / Toggle / MultiSelect / ColorPicker / KeyBindCapture), `depends_on` (cross-key dependencies), `ai_hint` (advice for AI agents tuning the value).

**Auto-generated UI** — `cf-tools-config-editor` reads schema and renders settings menu:

```

|--------------------------------|
| Text scale          [▶━━━━] 1.0 |
| (Slider 0.5 → 4.0 step 0.25)   |
| High contrast       [ON] [OFF] |
| Caption mode    [Standard ▼]   |
| Caption categories             |
| ☑ Combat ☑ Mission ☐ AI       |
| Reduce camera shake [██━━] 0.5 |

**Audit log** — every settings change logged with timestamp + actor_id + key + from_value + to_value + source_tier + reason + session_id + replay_event_id. Persists across sessions; queryable via `cfctl admin audit log --filter key=<key>`.

**Profile export/import** — `cfctl profile export ~/Downloads/my_profile.json` + `cfctl profile import`. Schema-versioned; migration runs on import; server-locked keys filtered.

**Diff display** — settings change UI shows old → new diff before applying:
```

**Schema versioning + migration** — when schema bumps (new key added or type change), `cfctl admin migrate-config` runs. Old profile.ron files auto-upgrade with default values. Backup of old file kept.

**Settings hot-reload watching (server)** — `cfctl admin watch-config <file>` watches for file change; auto-applies changes when file saves (player-friendly external editor workflow).

### Settings hierarchy resolution algorithm

```text
For each settings key requested:
  1. Read from Engine defaults
  2. Override with System config (if not locked-by Engine)
  3. Override with Profile config (if not locked-by lower tier)
  4. Override with Scenario config (if not locked-by lower tier)
  5. Override with Server config (if not locked-by lower tier)
  6. Override with Session config (if not locked-by lower tier)
  7. Override with Runtime cfctl (if not locked-by lower tier)
  8. Apply final value

  If lower tier attempts to override locked key:
    → emit `settings.override_rejected` event
    → reject change
    → keep current value
```

### Replay determinism + settings

Per DR-052: replay determinism requires settings be fully captured in run bundle:

- `run_manifest.json.settings` contains the **resolved settings** at run start (after hierarchy cascade)
- `run_manifest.json.settings_origins` records which tier set each key value (for audit)
- Replay verifier loads these settings before replay
- Live settings changes (`act.settings.set`) are recorded in events.jsonl
- Replay reproduces same settings deltas at same ticks

### Tutorial + onboarding for settings (DR-023 integration)

- First-time launch: tutorial walks player through profile.ron setup (no manual file editing)
- Per-screen settings panels (M2.2C + M8): 6-tab menu (Graphics / Audio / Controls / Accessibility / Gameplay / Language) auto-generates UI from schema
- Server browse (M9): shows per-server settings summary (anti-cheat / mods / difficulty) before player joins
- Settings change captions: every change emits `settings.changed` caption ("Set sound volume: 0.8")

### Config migration on schema bump (DR-029 parity)

When schema version bumps (e.g. new settings key added):

- Engine includes a migration handler for each schema version
- Old `profile.ron` files auto-upgrade with default values for new keys
- Migration runs on launch; backup of old file kept
- Server admins can manually migrate via `cfctl admin migrate-config`
