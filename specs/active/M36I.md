# M36I — Steam Achievements Deep + Cloud Saves + Workshop API Deep + Rich Presence + EOS Adapter Deep

## Status

`active`

## Intent

**M36I is the platform integration deep-dive milestone** — closes the surface-level "Steam SDK" / "Workshop integration" / "Achievements bridge" / "Cloud saves" / "Rich Presence" / "EOS adapter" mentions in M36A with full per-feature kernels. M36A wired the SDK adapters and proved "Steam Cloud sync works"; M25A authored 75 achievement strings; M27 defined the unlock-tracking event family. None of those answer the questions a Steam release actually needs: **per-achievement unlock condition + reward + visible-vs-hidden metadata for every one of 75+ achievements; cross-machine Cloud save conflict resolution that doesn't lose work; Workshop upload + version + revision + dependency + reverse-dependency + collection management; rich-presence state machine across 6+ player states; EOS adapter cross-platform friend list with per-shard status**. M36I ships all of it.

M36I promise: **"every one of the 75+ M25A achievements has a concrete unlock condition + Steam metadata + visible/hidden flag + optional reward; Cloud saves sync across machines with deterministic conflict resolution (latest-tick-wins default + manual merge UI for ties); Workshop authors can upload + revise + version + manage dependency chains + assemble collections from inside the game; the player's rich-presence string updates correctly across in-mission / in-base / on-orbit / spectating / matchmaking / browsing-workshop states; and EOS-authenticated friends appear in the friend list with per-shard online status, alongside Steam friends, with cross-platform invite working both directions."**

## Player-facing behavior

### Per-achievement deep design (75+ achievements from M25A bible)

Every achievement in `content/narrative/achievements/achievements_strings.ron` is promoted to a full `cf-achievement` definition with the following per-achievement fields:

| Field | Type | Notes |
|---|---|---|
| `id` | string (slug) | Stable identifier; matches Steam achievement API name |
| `display_name` | string (i18n key) | From M25A strings |
| `description` | string (i18n key) | From M25A strings; hidden achievements show "???" until unlocked |
| `unlock_condition` | enum-tagged | One of: `event_count`, `event_streak`, `cumulative_stat`, `combo`, `time_window`, `state_match`, `meta_progress` |
| `unlock_target` | structured | The threshold / event family / state predicate that satisfies the condition |
| `visibility` | enum | `visible_always` / `visible_after_unlock` (hidden until earned) / `visible_after_prerequisite` (shows after a related achievement unlocks) |
| `category` | string | Combat / Survival / Engineering / Medical / Faction / Boss / Collection / Multiplayer / Storyteller / Hidden / Accessibility / Modding (12 categories from M25A) |
| `tier` | enum | `bronze` / `silver` / `gold` / `platinum` (cosmetic only — Steam icon color) |
| `reward` | optional | Profile-only cosmetic (skin / palette / nameplate / loading-tip unlock / codex unlock) — DR-031 cosmetic-only |
| `steam_metadata` | structured | `steam_api_name`, `icon_unlocked.png`, `icon_locked.png`, `progress_stat` (Steam stat for progress bars), `points` (Steam-tracked) |
| `dependent_on` | optional list | Achievements that must unlock first (for chains; e.g., "Hollow King defeated" depends on "First Boss Defeated") |

The full table of 75+ is authored in `game/content/achievements/registry.ron` and split per-category files (`combat.ron`, `survival.ron`, ...). Cardinality target: ≥75 achievements, expandable post-launch via additive content patches.

The achievement engine (`cf-achievement-engine`) subscribes to the canonical event bus and evaluates unlock conditions per tick:
- `event_count`: counter increments on matching event; unlock at threshold
- `event_streak`: consecutive matching events with reset rules per spec
- `cumulative_stat`: total stat value (kills / distance / heals / etc.) reaches threshold
- `combo`: ordered or set-required matching events within a time window
- `time_window`: a state held for N consecutive ticks
- `state_match`: a profile/save predicate matches at unlock-evaluation time
- `meta_progress`: post-mission meta-state crosses threshold

On unlock: emits `achievement.unlocked { id, tick, profile_id }`; calls `cf-platform-steam::achievement_unlock(steam_api_name)`; awards the reward to the profile; appends to "Recently Unlocked" UI strip. Steam Achievements API is one-way (cannot be programmatically unset); the engine respects this — local re-unlock is no-op after first.

Hidden achievements: `visibility=visible_after_unlock` mods both the display name and description to "???" / "Hidden achievement" in pre-unlock state; the Steam metadata still uploads to Steam but Steam's "hidden" flag is set. Steam's UI handles its own hidden-state rendering.

### Cloud save format + cross-machine sync + conflict resolution

Cloud saves use a canonical, versioned envelope:

```ron
CloudSaveEnvelope {
    schema_version: 1,
    profile_id: "...",
    written_at_unix_ms: 1747400000000,
    written_on_machine_id: "...",       // anonymized HMAC of stable machine fingerprint
    tick_at_write: 184_320,             // sim tick at save time (deterministic ordering key)
    save_kind: enum { Profile, Mission, RunBundle, ModBucket },
    payload_sha256: "...",
    payload: Vec<u8>,                   // canonical-encoded DR-029 SaveBlob
}
```

Per-platform Cloud adapters (Steam Cloud, EOS Cloud) implement upload + download + list-versions of these envelopes. The save model:

- **Per-profile sync**: profile.ron + per-mission saves + run-bundles + per-mod save buckets
- **Versioning**: each Cloud slot keeps the last 5 versions per save_kind (Steam's default rolling history)
- **Determinism check on load**: payload_sha256 verified pre-deserialize; mismatch → reject + fall back to next-newest version
- **Quota**: respect Steam Cloud 100 MiB default (configurable in Steam appmanifest); evict oldest run-bundle if quota exceeded; profile.ron + mission saves NEVER evicted

**Conflict resolution** when two machines have written different saves to the same slot since last sync:

| Scenario | Resolution |
|---|---|
| `tick_at_write` differs | Default: latest tick wins (more gameplay = more recent). Older save kept in conflict-history slot for 7 days, recoverable via UI. |
| `tick_at_write` identical, `written_at_unix_ms` differs | Latest wall-clock wins; older preserved in conflict-history. |
| `tick_at_write` + `written_at_unix_ms` both identical (truly racy) | Manual-merge UI appears at next launch: "Two saves match exactly; pick which one to keep." Both kept in history until choice. |
| Different `save_kind` per slot (corrupt) | Hard refuse; surface error; user asked to file bug |

A "Cloud Saves" tab in settings exposes the conflict-history slots, version timeline (last 5 per save_kind), and a manual "Force this version" override. Every conflict resolution emits `cloud.conflict_resolved { save_kind, resolution, winning_machine_id }`.

The latest-tick-wins default is justified by: (a) sim tick is deterministic and increases monotonically within a profile's playtime; (b) wall-clock alone is unreliable across machines with clock drift; (c) tick is the canonical gameplay-progress proxy.

### Steam Workshop API deep integration

Building on M33 + M33C + M36A's Workshop surface, M36I closes the remaining authoring + collection flows.

**Upload + revision flow**:
- `act.player.workshop_publish { mod_dir }` packages mod (per M33), computes manifest, generates preview thumbnail or uses author-provided, uploads via Steam UGC API
- First-time publish: creates Workshop item; assigns Workshop ID; writes `mods/<slug>/.workshop_id` for future updates
- Subsequent publishes are revisions: increment manifest `revision: u32`; uploads new payload; previous payload retained as a Workshop history entry; changelog input prompted
- Each revision tagged with author-supplied version string (semver) + a Corefall build-id (engine version compatibility hint)
- Authors can mark a revision as `pre_release` (hidden from default subscribers; opt-in beta channel)

**Version channels**:
- `stable`: default channel; subscribers auto-update (per M33C rules)
- `pre_release`: opt-in channel for beta testers; per-subscriber toggle on the mod card
- `archived`: read-only legacy; authors can flag deprecated revisions; new subscribers default to latest stable

**Dependency declarations + reverse-dependency discovery**:
- Manifest declares forward dependencies (per M33C): `dependencies: [{ id, min, max }]`
- Workshop indexes reverse-dependencies: querying mod X surfaces "12 mods depend on this"
- Subscribing to a dependent mod prompts: "This mod requires <dep>; subscribe to <dep> too?"; one-click subscribes the dependency chain transitively
- Unsubscribing from a mod that has reverse-dependencies in your local subscriptions warns: "3 of your subscribed mods depend on this; they may stop working" with [Unsubscribe Anyway] / [Cancel] actions
- Dependency cycles in the global Workshop graph are flagged but allowed (Workshop is open; M33C quarantines cycles at load time only)

**Collection management**:
- Authors / curators can assemble Workshop collections — ordered or unordered groupings of mods (e.g., "MyOverhaulPack: 12 mods that work together")
- `act.player.workshop_collection_create { name, description, mod_ids }` creates a collection
- `act.player.workshop_collection_subscribe { collection_id }` subscribes to all mods in the collection atomically; dependency-resolves transitively
- Collections support per-mod ordering hints that override default load-order priority (advisory; M33C resolver still owns the authoritative order)
- Players see "Collection inherited" badge on mods subscribed via a collection; un-following a collection unsubs the un-individually-subscribed mods only

**Workshop metadata sync**: every subscribed mod's stars + review count + last-updated timestamp fetched via Steam UGC API on a 6h cadence; surfaces in the browser without leaving the game.

### Rich presence state machine

The player has exactly one rich-presence state at any tick. Both Steam and Discord adapters consume the same state machine.

| State | Trigger | Steam string template | Discord string template |
|---|---|---|---|
| `in_mission` | Inside an active scenario tick | `In mission: {scenario_display_name} ({faction_display_name})` | `Mission: {scenario_display_name}` |
| `in_base` | At the player's persistent base / hub | `In base: {base_display_name}` | `In Base` |
| `on_orbit` | In the orbital map / fleet view | `On orbit: {orbit_display_name}` | `In Orbit` |
| `spectating` | Watching a replay or another player live | `Spectating: {target_display_name}` | `Spectating {target_display_name}` |
| `matchmaking` | In the lobby browser or party-finder queue | `In matchmaking: {region} / {mode}` | `Looking for match` |
| `browsing_workshop` | In the mod browser | `Browsing Workshop` | `Browsing Workshop` |
| `in_menu` | Main menu / settings / no other state active | `In menu` | `Idle in Menu` |

Each rich-presence state carries optional structured context (party_size / party_max / join_secret / spectate_secret / scenario_id / replay_id) per platform.

**State transitions** are driven by the canonical engine state, NOT polled. A `cf-platform-common::PresenceState` enum is updated by:
- `cf-mission-runner` (mission start / end)
- `cf-base` (base enter / leave)
- `cf-orbit` (orbit enter / leave)
- `cf-replay` (spectate start / stop)
- `cf-matchmaking` (queue enter / leave)
- `cf-app::mod_browser` (browser open / close)

The state machine emits `presence.state_changed { from, to, context }` events for audit. Rate-limited to 1 update per second (Discord API limit); per-platform adapters de-dup identical states.

**Party + join secrets**: when `in_mission` with co-op, the adapter generates a per-session join secret; friends clicking "Join" on the Steam/Discord overlay get a deep-link launch flag (`--join-secret=<...>`) that auto-joins the lobby via `cf-server` (per M36).

### EOS adapter deep + cross-platform friends

Building on M36A's EOS adapter scaffold:

**Authentication**:
- EOS Account Service login flow (PKCE OAuth via embedded WebView or system browser per platform)
- Login result persisted as encrypted token in `cf-platform-eos::session.bin`
- Optional Steam-EOS bridging: a Steam-authenticated player can opt-in to link their EOS account for cross-platform friends (one-time PKCE flow)
- Anonymous EOS login also supported (limited functionality; no cross-platform friend list)

**Cross-platform friend list**:
- The unified friend list aggregates Steam friends + EOS friends + (future) other platform adapters
- Per-friend platform tag: `[Steam]` / `[EOS]` / `[Anon]`
- Per-friend online status + current rich-presence state (from the state-machine table)
- Per-shard status: if the player + friend are in different MMO shards (per DR-035), the friend's status includes `(Shard: <name>)` suffix; same-shard friends omit the suffix
- Friend invites work both directions: Steam → EOS invite generates a join URL the EOS player can paste in their EOS client; EOS → Steam invite generates a Steam URL

**Per-shard friend status**:
- `cf-server` exposes per-shard player presence via the lobby directory
- The friend-list adapter queries `cf-server::lobby_directory::find_player(friend_id)` to resolve shard membership
- A friend on a private (password-locked) shard shows status as "On private shard"; the shard name is hidden unless the friend's shard is in the player's known-shards list

> **Cross-spec gap declared**: the `cf-server::lobby_directory::find_player(friend_id)` API does NOT yet exist in the M36 dedicated-server scaffold. M36I depends on it but cannot ship the per-shard friend status without it. This gap is tracked as a TODO against M36 — M36 must add `find_player(friend_id) -> Option<(shard_id, presence_state)>` to its lobby directory surface as a precondition for M36I closure. If M36 has already closed at the time M36I starts, M36I owns the additive API extension to `cf-server::lobby_directory`.

**Cross-platform party**:
- Steam + EOS players can join the same lobby via the lobby directory (M36)
- Per-platform invite-link generation handled by the respective adapter
- The lobby UI surfaces each member's platform tag

## Acceptance criteria

```gherkin
Scenario: Event-count achievement unlocks at threshold
  Given an achievement "kill_100_husks" with unlock_condition=event_count
    And unlock_target={ event_family: "combat.enemy_killed", filter: { faction: "husks" }, threshold: 100 }
  And the player has killed 99 husks across this profile
  When the player kills one more husk and combat.enemy_killed fires
  Then cf-achievement-engine evaluates and matches the unlock condition
  And achievement.unlocked fires with id="kill_100_husks" + tick=T
  And cf-platform-steam::achievement_unlock("KILL_100_HUSKS") is called
  And the "Recently Unlocked" strip surfaces the achievement for 8 seconds

Scenario: Hidden achievement displays placeholder until unlock
  Given an achievement "secret_husk_overlord" with visibility=visible_after_unlock
  When the player opens the achievement browser before unlocking
  Then the achievement card shows display_name="???" + description="Hidden achievement"
  And the locked icon is rendered
  And the Steam metadata's hidden flag is true
  When the player satisfies the unlock condition
  Then the same card updates to display the real display_name + description
  And the unlocked icon replaces the locked icon

Scenario: Combo achievement requires ordered events within window
  Given an achievement "perfect_breach" with unlock_condition=combo
    And unlock_target={ ordered: true, events: ["breach.charge_placed", "breach.charge_detonated", "combat.enemy_killed*5"], window_ticks: 600 }
  When the player executes the 3-event sequence within 600 ticks
  Then cf-achievement-engine matches the combo
  And achievement.unlocked fires
  When another player executes the sequence with the 5 kills BEFORE the charge_detonated
  Then the combo does NOT match (ordering violated)
  And no achievement.unlocked fires

Scenario: Dependent-chain prerequisite blocks unlock
  Given achievement "hollow_king_defeated_3_ways" depends on "hollow_king_defeated"
  And the player has NOT unlocked "hollow_king_defeated"
  When the player satisfies "hollow_king_defeated_3_ways" condition
  Then cf-achievement-engine refuses the unlock
  And achievement.unlocked does NOT fire for "hollow_king_defeated_3_ways"
  When "hollow_king_defeated" later unlocks
  Then on the next evaluation tick "hollow_king_defeated_3_ways" unlocks (with the prior matched state)

Scenario: Cloud save latest-tick-wins on conflict
  Given Machine A wrote profile.ron at tick 18_500 + unix_ms 1_000
  And Machine B wrote profile.ron at tick 12_000 + unix_ms 5_000 (Machine B's wall clock is later but tick is earlier)
  When the player launches on Machine C and cf-cloud-sync pulls both versions
  Then cf-cloud-conflict::policy applies latest-tick-wins
  And Machine A's profile.ron is loaded (tick=18_500 > 12_000)
  And Machine B's profile.ron is preserved in the conflict-history slot for 7 days
  And cloud_conflict_resolved fires with resolution="latest_tick" + winning_machine_id=hash(Machine A)
```

## Out of scope

- **Steam Achievements reset / unset** — Steam API is one-way for unlock; M36I respects this. Profile-side reset is a future debug tool, never user-facing.
- **Cloud save encryption at rest beyond Steam Cloud / EOS Cloud defaults** — Steam handles transport encryption; M36I does not add a second layer.
- **Cross-Steam-account migration of saves** — a save belongs to one Steam account; Steam-EOS account-link does NOT migrate saves between accounts.
- **Workshop monetization mechanics** — M33E owns this; M36I only surfaces revenue-share opt-in toggle without payment processing.
- **PSN / Xbox / Switch friend integration** — console SDK adapters are post-launch DLC scope per M36A.
- **Discord voice channel auto-join from rich presence** — voice is M37 / M37A scope; M36I only sets the rich-presence string.
- **Per-achievement leaderboards** — Steam Stats leaderboards are M41B scope; M36I tracks progress only.
- **Manual conflict-merge with field-level granularity** (e.g., merge equipment from one save + base from another) — M36I offers version-level merge only; field-level is too risky for save integrity.
- **EOS Voice / EOS Lobbies replacing Steam Lobbies** — EOS adapter complements Steam, doesn't replace it.

## Notes for the implementer

- **Achievement evaluator is deterministic per-tick**: subscribe to the canonical event bus; never sample wall-clock; never use `HashMap` iteration. Use `BTreeMap<AchievementId, EvaluatorState>` so the same event sequence on two machines produces identical unlock-order events.
- **Steam Achievement API one-way constraint**: design every condition so unlocks are monotonic and additive. If a player legitimately satisfies a condition, then later reduces their stat, the achievement stays unlocked. Per-tick evaluation must short-circuit on already-unlocked achievements; no re-evaluation cost after unlock.
- **Per-achievement icons**: M48B baked placeholders are acceptable for M36I closure; commercial-grade icons follow in Tier 3 polish. Both unlocked + locked variants required per achievement (Steam expects both URLs).
- **Hidden achievement Steam metadata**: even hidden achievements must register with Steam at app startup; Steam's UI handles the per-user hidden-state rendering. Do NOT skip registration for hidden ones.
- **Cloud envelope determinism**: `tick_at_write` MUST come from the canonical sim tick (deterministic, monotonic per-profile). Wall-clock is informational only and never primary for conflict resolution.
- **Cloud quota enforcement**: 100 MiB Steam default; run-bundles are first to evict (largest + most replaceable); profile.ron + mission saves are never evicted. EOS Cloud has its own quota; adapter surfaces both.
- **Conflict-history retention is 7 days** for evicted-loser versions; after 7 days they are GC'd to free Cloud quota. Surface the GC date in the Cloud Saves settings UI so the player knows when a version becomes unrecoverable.
- **Workshop revision uploads can fail mid-upload** (network drop, Steam UGC rate limit): make the upload resumable; persist a `.upload_in_progress` marker; retry on next launch if interrupted.
- **Pre-release channel UI**: surface the channel toggle on a per-mod basis; default OFF; channel preference persists in profile, not save (cross-profile portability).
- **Reverse-dependency index** must be local-only for the player's subscribed set; global reverse-dep queries (cardinality across all of Workshop) defer to Steam's UGC API to avoid duplicating Steam's index.
- **Collection subscribe-all is atomic from the player's POV**: if any mod in the chain fails to download, the whole operation rolls back (unsubscribes the partial set). This avoids the "half-subscribed" surface that M33C's load-order resolver would treat as a dependency-missing state.
- **Presence state-machine rate limit**: Discord allows 1 update/sec; Steam is more generous but consistent rate-limiting prevents flicker. Dedup logically identical states (same enum + same context) — never emit a transition event for a no-op transition.
- **Presence join-secret** is a per-session opaque token; never include user PII. Regenerate per session; expire when the session ends.
- **EOS account-link is one-way bridging only** — Steam-EOS link establishes a presence-discovery channel; it does NOT migrate game state. Be explicit in the UI: "This links friend lists, not saves."
- **Cross-platform invite** must respect each platform's policy for invite links; Steam's invite-link format is `steam://joinlobby/<appid>/<lobby_id>/<owner_steamid>`; EOS uses its own deep-link format. Adapter abstracts both.
- **Per-shard status security**: never leak private-shard names; the friend list shows "On private shard" with no name unless the local player is also on that shard or has been previously invited.
- **Schema migration**: `CloudSaveEnvelope::schema_version` is 1 at M36I close; design the reader to accept and migrate from future versions without breaking.
- **Performance budget**: per-tick achievement evaluation must complete in ≤0.5ms over the 75-achievement registry at a typical 60Hz tick rate. Defer heavy `state_match` predicates to end-of-tick evaluation.
- **Determinism gate**: M36I MUST pass DR-049 cross-platform CI; any non-deterministic ordering in achievement / cloud / workshop / presence event emission is a hard fail.
