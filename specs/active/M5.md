# M5 — Equipment, Chassis, And Damage Grammar

## Status

`active`

## Intent

The chassis grammar from DR-014/021 works on the native engine. One powered-armor actor and one light-mech actor exercise the full ladder of body zones, layered armor, modules, damage stages, weapon jams, pilot eject, repair, and salvage. Limb damage has visible mechanical consequences. The pilot can eject from a wrecked mech and continue as foot infantry.

## Player-facing behavior

- The player picks a chassis at scenario start: infantry (default), powered armor (Spartan-ish), or light mech (~3× human).
- Each chassis has a body graph: 15 zones (head, torso, arms, forearms, hands, legs, shins, feet, backpack), 14 joints, 5 equipment sockets.
- Armor is layered: External → Internal → Core → wound. Each layer has its own HP and hardness.
- Modules: jet, shield, sensor, repair-drone, weapon-mount. Each module has state Nominal → Degraded → Warning → Failed → NotPresent.
- Damage stages: nominal → degraded → module-warning → module-failed → weapon-jammed → armor-cracked → disabled → pilot-injured → eject → bail-too-late → wreck → gibbed/exploded.
- Limb damage has consequences: limp on leg loss, one-arm rifle handling on arm loss, dropped gear on hand loss, disabled grip, reduced climb/jump/jet.
- Pilot eject works: when chassis stage hits eject, the pilot detaches (shown as a separate small actor) and can continue. If the eject window expires, bail-too-late.
- Chassis salvage: after wreck, the player can salvage modules with `act.chassis.salvage` and pick up recoverable parts.
- Repair: `act.chassis.repair --zone <zone>` repairs a damaged zone (consumes repair-drone capacity if present).

## Acceptance criteria

```gherkin
Scenario: Player progresses through damage stages with HUD parity
  Given a powered-armor pilot at full HP
  When the pilot takes increasing damage
  Then chassis.stage_changed fires for each transition: nominal → degraded → module-warning → module-failed → armor-cracked → disabled → pilot-injured
  And the HUD STAGE label updates to match
  And cfctl observe.actor.chassis.stage matches the live state at every tick

Scenario: Body graph is inspectable via cfctl
  Given a powered-armor pilot
  When cfctl inspect.chassis player runs
  Then the response includes body graph (15 zones + 14 joints + 5 sockets)
  And per-zone integrity (HP per layer)
  And per-module state
  And eject_ticks_remaining + eject_ticks_total

Scenario: Walk/run/crouch/climb/jet are not static slides
  Given a chassis actor moving
  Then animation-state events (or placeholder animation-state events) fire for stance + foot-contact + upper-body aim
  And the rendered sprite shows walk-cycle offsets, not a constant pose
  And the actor never appears as a "static sliding pawn"

Scenario: Limb loss has mechanical consequences
  Given an arm zone destroyed (HP=0 across all 3 layers)
  Then the actor's rifle handling switches to one-arm mode (visible in HUD or stance)
  And dropped gear emits an event if the lost limb was holding equipment
  Given a leg zone destroyed
  Then the actor's gait shows a limp (animation event) and movement speed drops
  And cfctl observe.actor reflects the reduced capability

Scenario: Module damage produces module-warning → failure
  Given a jet module taking damage
  When the jet HP crosses the warning threshold
  Then chassis.module_state_changed fires with from=Nominal, to=Warning, module=Jet, reason="<damage_label>"
  When the jet HP crosses the failure threshold
  Then chassis.module_state_changed fires with to=Failed
  And the player can no longer use act.player.jet (rejected with reason="module_failed")

Scenario: Pilot eject works
  Given a pilot inside a wrecked chassis (stage=disabled)
  When act.player.eject is invoked
  Then chassis.pilot_ejected fires
  And the pilot detaches as a separate actor (Stance::Ejecting → Ejected)
  And the player can continue moving as foot infantry
  When the pilot enters the extraction zone
  Then chassis.pilot_extracted fires and mission.mission_resolved fires with result=won

Scenario: Eject window can be missed (bail-too-late)
  Given a chassis hitting stage=eject
  When the player does not invoke act.player.eject within EjectWindow.ticks
  Then chassis.pilot_bailed_too_late fires
  And the pilot dies inside the chassis

Scenario: Chassis salvage emits recoverable modules
  Given a wrecked chassis with surviving modules
  When act.chassis.salvage is invoked
  Then chassis.salvaged fires with a list of recoverable module ids
  And those modules are added to the player's inventory (or scenario salvage zone)

Scenario: Chassis repair restores zone HP
  Given a damaged torso zone (HP=50% across layers)
  When act.chassis.repair --zone torso is invoked
  Then chassis.repaired fires with zone=torso, hp_delta>0
  And zone HP increases (capped at max)
  And cfctl observe.actor.chassis.zones[torso] reflects the new HP

Scenario: Weapon jam + clear
  Given a rifle with jam_chance>0
  When the rifle jams (random roll on fire)
  Then chassis.weapon_cleared=false (jam state) and equipment.weapon_jammed fires
  And subsequent fire is rejected
  When act.chassis.clear_jam is invoked
  Then chassis.weapon_cleared=true and the rifle can fire again

Scenario: Save round-trips chassis state
  Given an actor with a damaged chassis
  When cf-save serializes and deserializes
  Then ChassisState round-trips bit-for-bit (per-zone HP, module state, pilot state, eject window remaining, weapon jam state)
  And SaveBlob.checksum (blake3) matches
  And SAVE_BLOB_VERSION=1 (or migration runs cleanly if bumped)

Scenario: Save round-trips actor M5 extension fields
  Given an actor with crouch_active=true, climb_active=false, jet_active=true
  When cf-save serializes and deserializes
  Then those flags round-trip
  And gear_dropped_by_limb_loss, chassis_detached, afflictions vec all round-trip via serde defaults

Scenario: Tutorial safety prevents lethal damage
  Given a scenario with tutorial_safety=true and a chassis pilot
  When the chassis takes lethal damage
  Then chassis.stage_changed caps at pilot-injured (not death)
  And no chassis.pilot_lost / chassis.pilot_separated event fires

Scenario: Equipment loadouts are data-driven
  Given content/equipment/loadouts/load_a_infantry.json
  When cf-equipment loads at scenario start
  Then the loadout is parsed from JSON (not hardcoded)
  And the same is true for load_a_powered_armor.json and load_a_light_mech.json
  And cf-mod validate content/equipment/ passes

Scenario: HUD module strip distinguishes placeholder vs chassis-backed
  Given an infantry actor (no chassis)
  Then HUD module strip shows placeholder=true and the M4A flat-rifle derivation
  Given a powered-armor actor with chassis
  Then HUD module strip shows placeholder=false and reads from chassis.modules
```

## Out of scope

- Full collision physics (limb-to-limb, projectile-projectile contacts) — M5.5
- Material kernel (sand falls, water pools, fire spreads) — M5.6
- Atmospherics (PV=nRT gas/liquid) — M5.9
- Universal gravity ballistic drag — M5.7
- Ricochets / tracer rounds — M5.5+ visual juice
- Body damage extension into M3B replay viewer — M3B done; chassis death events feed it
- M5.10 worlds / factions / narrative — BP6+

## Dependencies

- M1 actor controller (must be done): ActorState, body status state machine.
- M2 chunked terrain (must be done): chassis movement collides with terrain pixels.
- M3A event recorder (must be done): chassis events flow into events.jsonl.
- M4A readability (must be done OR concurrent): HUD silhouette + module strip read chassis state.

## Notes for the implementer

- The 3 chassis archetypes (`infantry_v1`, `powered_armor_v1`, `light_mech_v1`) live in `cf-chassis::spec`. Half-extents: infantry 8x16, powered armor 10x20, light mech 18x36. Visual proportion (Spartan-ish, mech-ish) is render-layer asset work, not sim data.
- `apply_zone_damage` MUST be monotonic on stage advancement — once stage=disabled, never goes back to nominal without explicit `repair` or `force_stage` (test-only).
- `EjectWindow.ticks` MUST be tick-rate-stable: at 120 Hz, the window in real seconds is the same as at 60 Hz. Use `from_real_seconds(seconds, tick_rate_hz)` for construction.
- LOAD-A loadouts must export to `content/equipment/loadouts/*.json` and be loaded at runtime — NOT hardcoded in Rust. The hardcoded versions in `cf-equipment::loadout::load_a_*` are the seed data the export script writes from.
- 7 cfctl methods + 13 chassis events: any future cf-control schema bump must include a migration shim. (Current policy: additive methods don't bump SCHEMA_VERSION; if you change a method's params shape, that's a bump.)
- Pilot eject is a real actor split: the pilot becomes a new ActorId with its own ActorState (no chassis attached). The chassis becomes a wreck (interactable for salvage). Don't model eject as a state flag on the same ActorId.
