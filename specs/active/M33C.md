# M33C — Mod Permissions + Trust Tiers + Cert Chain + Conflict Resolution + Steam Workshop Deep

## Status

`active`

## Intent

**M33C is the mod ecosystem trust + load-order deep-dive milestone** — closes the surface-level "Workshop integration" + "trust tier policy" mentions in M33 / M36 / M36A with a full kernel: 4 trust tiers (`vanilla` → `verified` → `community` → `experimental`) + cert chain signing for `verified` mods + per-mod load-order + override + dependency graph + per-conflict diagnostic UI + Steam Workshop upload / subscribe / auto-update / version-pin flow. After M33C, a player can stack 50 mods, see exactly which mod overrides which file, lock specific versions, and trust the badge that says a mod is signed.

M33C promise: **"a player can subscribe to 50 Workshop mods, the load-order panel shows every override and every conflict, signed mods carry a verifiable badge from a known author, and reverting a broken update is one click — all without leaving the game."**

## Player-facing behavior

### 4 trust tiers

Every mod, on first load, is classified into exactly one tier. Tier governs (a) which Lua capabilities the mod may request (per M33B), (b) whether the mod can persist save-game state, (c) whether the mod can participate in ranked / competitive sessions, (d) the badge shown in the mod browser.

| Tier | Signature requirement | Capabilities granted | Save-game persistence | Competitive eligible | Browser badge |
|---|---|---|---|---|---|
| `vanilla` | Engine-signed bundled content | All (engine internal) | Yes | Yes | green "Official" |
| `verified` | Author cert chained to Corefall root CA | `sim_read`, `sim_write`, `event_emit`, `session_read`, `ui_overlay` | Yes | Yes (allow-list per leaderboard) | blue "Verified" |
| `community` | Workshop SHA256 only (no chained cert) | `sim_read`, `event_emit`, `ui_overlay` | Yes | No | yellow "Community" |
| `experimental` | Local-only or sideloaded zip | `sim_read` | No (warns on load) | No | red "Experimental" |

Player can raise a mod's tier manually via the mod browser (e.g. promote a `community` mod to `verified`-equivalent locally); doing so emits `mod.trust_overridden { mod_id, from, to }` to the run-bundle for audit. Demotion (signature stripped, dependency missing) is automatic.

### Cert chain for signed mods

`verified`-tier mods carry a detached signature file (`mod.sig`) chained to a Corefall root CA shipped with the engine.

- Root CA public key embedded in `cf-engine` binary (1 root + 3 backup roots; rotation policy per ops doc)
- Each author CSR signed by a Corefall intermediate CA (offline; out-of-band; community PR + manual review)
- Per-release mod artifact signed by the author's leaf cert
- Engine verifies: leaf → intermediate → root, expiry, revocation list (`mod_revocation.json` shipped + Workshop-fetched)
- On signature failure: tier demoted to `community`; `mod.cert_invalid { reason }` event fires; player sees yellow badge instead of blue
- Revocation: leaf cert listed in revocation list → mod refused entirely; clear UI banner explains

### Mod load-order resolution

Mods load in deterministic order computed from:

1. Manifest `priority: i32` (default 100; range -1000 to +1000)
2. Manifest `dependencies: [<mod_id>]` — DAG; topological sort guarantees deps load first
3. Manifest `load_after: [<mod_id>]` / `load_before: [<mod_id>]` — soft hints; engine resolves into the partial order
4. Tier breaks ties: `vanilla` > `verified` > `community` > `experimental`
5. Lex order on mod_id breaks ties when all of the above are equal

Result: a fully-deterministic load order printed at startup, captured in the run-bundle as `mod.load_order { sequence }`. Same set of mod hashes on two machines yields the same order.

Cycle detection: a dependency cycle is a hard error; the cycle is reported in the load-order panel; cycling mods are quarantined (not loaded); session continues with non-cycling subset.

### Per-mod conflict diagnostic UI

When two mods declare the same resource (same actor id / same weapon id / same Lua callback target / same recipe id), the load-order panel surfaces the conflict.

- Conflict categories: `content_override` (same id; later mod wins), `lua_callback_shadow` (both mods register OnFire for same weapon; chain executes both in load-order), `recipe_collision` (same craft inputs map to different outputs; later mod wins), `material_id_collision` (same material id with different physical properties — refused; both flagged), `manifest_field_collision` (both mods modify the same scenario file)
- Each conflict row: `[icon] <ModA> ↔ <ModB>: <field/id>: <resolution>` with a [Detail] expand
- Resolutions available per row: `accept_default` (load-order), `prefer ModA`, `prefer ModB`, `disable ModA`, `disable ModB`, `pin ModA to version X` (when version pinning available)
- Player choice is persisted as `mod.conflict_resolution.<conflict_key>` in profile; applied on next reload
- `material_id_collision` is non-overridable (gameplay safety); both mods refuse to coexist; player must disable one

### Steam Workshop deep integration

Building on M36A's Workshop surface:

- **Upload**: `cargo run -p cf-mod -- workshop publish <mod_dir>` packages mod (per M33), generates preview thumbnail (or uses author-provided), uploads `.cfmod` + `mod.sig` (if signed) + changelog; Steam Workshop entry created or updated
- **Subscribe**: clicking subscribe in the in-game browser triggers Workshop API; download + verify + install to `mods/workshop/<workshop_id>/`
- **Auto-update**: per-mod auto-update toggle (default ON for `verified`, OFF for `community`/`experimental`); on game start, engine queries Workshop for each subscribed mod's current published version; mismatch + auto-update=ON → download + reload; mismatch + auto-update=OFF → "Update available" badge in browser
- **Version pinning**: `mod.version_pin { mod_id, version }` set via UI ("Pin this version"); engine refuses auto-update for pinned mods; pin survives reinstalls
- **Rollback**: every applied update keeps the previous artifact for 30 days; "Roll back to <version>" one-click in the browser
- **Unsubscribe**: Workshop unsubscribe → mod files moved to `mods/.trash/` for 7 days, then deleted; meanwhile player can restore

### Dependency graph + missing-dep handling

Mod manifest declares dependencies with version ranges:

```ron
dependencies: [
    { id: "core_extension_pack", min: "1.2.0", max: "1.x" },
    { id: "physics_helpers",    min: "0.4.0" },
]
```

- Resolver walks the graph at startup; missing deps → mod refused (not loaded) with banner: "Mod `<name>` requires `core_extension_pack ≥ 1.2.0` — [Subscribe] [Disable Mod]"
- Subscribing the missing dep triggers download + retry of the original mod
- Version conflict (two mods require incompatible ranges of same dep) → both mods quarantined; conflict panel surfaces the range mismatch with an [Auto-resolve] button that picks the broadest-compatible version

### Mod-version pinning + lockfile

Per-profile `mod_lockfile.ron` stores:

```ron
mods: {
    "core_extension_pack": { version: "1.2.3", sha256: "...", pinned: true },
    "scenic_pack":         { version: "0.8.1", sha256: "...", pinned: false },
}
```

- Locked sets reproduce reproducibly across machines (export / share)
- Pinned versions refuse auto-update; unpinning + relaunch picks up latest within range
- Share-link encodes the lockfile + Workshop ids; recipient applies via `act.player.mod_lockfile_import { url }`

### Per-mod sandbox quotas

Beyond M33B's per-callback CPU budget, M33C adds per-mod resource quotas:

- Heap: 32 MiB / mod (warning at 24 MiB; refusal at 32 MiB → mod quarantined for session)
- Asset disk footprint: 512 MiB / mod (warning at 384 MiB; install refused at 512 MiB)
- Persistent save bytes: 256 KiB / mod (oldest entries evicted FIFO past the cap)
- Per-tick total scripts CPU across all mods: 50 % of frame budget at configured tick rate; over-budget → load-order-last mods throttled first

### Mod browser deep

In-game mod browser (extends M33A surface):

- Tabs: `Installed`, `Workshop`, `Local`, `Conflicts`, `Updates`
- Per-mod card: badge (tier) + name + author + version + size + dependencies + capability summary + screenshot
- Filters: tier, search, author, tag, dependency, last-updated
- Sort: alpha, recently-updated, most-subscribed, smallest-size
- Per-mod actions: subscribe / unsubscribe / pin / rollback / view docs / report
- Per-author follow: subscribe to all of an author's mods
- Per-collection: Workshop-style collections supported (subscribe a collection → subscribes every mod in it)

## Acceptance criteria

```gherkin
Scenario: 4 trust tiers classify mods correctly at load
  Given a mod set containing
    | mod              | signed | source        | expected_tier |
    | bundled_pack     | engine | content/      | vanilla       |
    | scenic_pack_v1   | yes    | workshop      | verified      |
    | physics_helpers  | no     | workshop      | community     |
    | sideload_test    | no     | local zip     | experimental  |
  When the engine loads them
  Then each mod's mod_load_order_resolved event records the expected_tier
  And the mod browser shows the corresponding badge color
  And the capability gate refuses any callback whose declared capabilities exceed its tier's allow-list

Scenario: Signed mod's badge falls back to community when signature invalid
  Given a verified-tier mod whose mod.sig has been corrupted
  When the engine loads it
  Then cert chain verification fails with reason="leaf_signature_mismatch"
  And mod_cert_invalid event fires
  And the mod is loaded at community tier (yellow badge), not refused
  And the mod browser shows a tooltip: "Signature failed verification; tier downgraded"

Scenario: Revoked author cert refuses load entirely
  Given a mod whose leaf cert appears in mod_revocation.json
  When the engine loads it
  Then mod_revoked event fires with mod_id + cert_serial
  And the mod is NOT loaded at any tier
  And the mod browser shows a red banner: "Author cert revoked: <reason from revocation entry>"

Scenario: Deterministic load order across two machines
  Given two engines with the same set of 12 mod hashes installed
  When each loads the mods at startup
  Then mod_load_order_resolved on both engines records an identical sequence
  And the per-mod load index is identical
  And cf-replay run-bundles diff cleanly on the load-order section

Scenario: Dependency cycle quarantines cycle members
  Given mods A → B → C → A (cyclic dependency)
  When the engine resolves the load order
  Then the cycle is detected by cf-mod-loader
  And mod_dependency_missing fires for each of A, B, C with reason="dependency_cycle"
  And A, B, C are NOT loaded; sim starts with the non-cycling subset
  And the conflict panel shows the cycle visually with [Resolve] options

Scenario: Recipe collision picks load-order winner with override available
  Given Mod_A and Mod_B both define recipe id "scrap_to_ingot" with different outputs
  And Mod_A loads before Mod_B
  When mod_conflict_detected fires for the recipe collision
  Then the load-order resolution applies Mod_B's output (later wins)
  When the player clicks [Prefer Mod_A] in the conflict panel
  Then mod_conflict_resolved fires with resolution="prefer_mod_a"
  And next reload applies Mod_A's output instead

Scenario: Material id collision is non-overridable; both refused
  Given Mod_X and Mod_Y both define material id "alchemic_precursor" with different physical properties
  When the engine loads them
  Then mod_conflict_detected fires with category="material_id_collision"
  And both Mod_X and Mod_Y are quarantined (neither loaded)
  And the conflict panel offers [Disable Mod_X] / [Disable Mod_Y] only; no merge/override option

Scenario: Workshop subscribe downloads, verifies, installs
  Given the player clicks Subscribe on Workshop mod id 9876543
  When act.player.mod_subscribe runs
  Then cf-mod-workshop downloads .cfmod + mod.sig
  And cf-mod-trust verifies signature; tier assigned
  And the mod installs to mods/workshop/9876543/
  And mod_workshop_subscribed event fires
  And the mod appears in Installed tab on next render

Scenario: Auto-update applies for verified, requires action for community
  Given player subscribed to a verified mod v1.0.0 and a community mod v1.0.0
  And Workshop now publishes verified v1.1.0 and community v1.1.0
  When the game starts
  Then the verified mod auto-updates to v1.1.0 and mod_workshop_auto_updated fires
  And the community mod stays at v1.0.0; an "Update available" badge appears in the Updates tab
  When the player clicks Update on the community mod
  Then it updates to v1.1.0 with a confirmation step

Scenario: Version pin refuses auto-update
  Given player has pinned Mod_Q at version 0.5.2
  When Workshop publishes Mod_Q v0.5.3
  Then the auto-update path skips Mod_Q
  And the Updates tab shows "Pinned: 0.5.2 (latest 0.5.3 available)" with [Unpin & update] action
  When the player clicks [Unpin & update]
  Then mod_version_pinned event fires with pinned=false
  And Mod_Q updates to v0.5.3

Scenario: One-click rollback to a prior version
  Given Mod_R updated from v2.0.0 to v2.1.0 within the last 30 days
  When the player clicks [Roll back to v2.0.0] in the mod card
  Then mod_rolled_back event fires with from=2.1.0 + to=2.0.0
  And v2.0.0 artifact (cached in mods/.history/) is reinstalled
  And v2.1.0 is moved to history slot (still recoverable for 30 days)

Scenario: Lockfile export + import reproduces mod set on another machine
  Given player invokes act.player.mod_lockfile_export to ~/my_modpack.lock.ron
  When a different machine imports the same lockfile via act.player.mod_lockfile_import
  Then every mod_id + version is subscribed + installed exactly per the lockfile
  And the sha256 of each installed mod matches the lockfile entry
  And load-order resolution yields identical order on both machines

Scenario: Per-mod heap quota quarantines runaway mod for the session
  Given a mod that allocates 40 MiB of Lua heap (above the 32 MiB cap)
  When allocation crosses 32 MiB
  Then mod_quota_exceeded fires with mod_id + resource="heap" + observed=40MiB
  And the mod's Lua isolate is torn down for the remainder of the session
  And the sim continues unaffected; load-order replays pick up the mod again next session

Scenario: Determinism across mod-trust + load-order + conflict events
  Given two engines running m33c_load_order_determinism.ron with same seed + same mod set hashes
  When 1200 ticks elapse covering trust assignment + load-order + 3 conflicts + 1 quota event
  Then every mod.* event matches in payload + order across the two engines
  And SaveBlob.checksum at tick 1200 is identical
```

## Out of scope

- Per-mod monetization / paid mods — DR-006 + DR-031 (anti-pay-to-win) explicitly oppose this; never in scope.
- Cross-platform mod fetch outside Steam Workshop (itch.io / GitHub mirror) — local sideload + zip import covers offline; deep platform-agnostic browser is M48+ ambition.
- Cryptographic signing of save files containing mod state — save signing is M36/M49 anti-cheat scope.
- Per-actor / per-room mod overrides — mod resolution is global; per-scenario `disable_mods: []` is M36 server policy.
- Mod-level telemetry collection beyond Workshop's existing analytics — Corefall does not ship its own telemetry channel.
- A user-facing CA store editor — root CAs are pinned in the binary; rotation is engine-release scope.

## Notes for the implementer

- **cfctl write-merge convention** — multiple specs each add ~5 cfctl methods to `cf-control/src/server.rs`; to avoid merge conflicts and tangled handlers, **M33C creates `game/crates/cf-control/src/m33c_actions.rs`** containing the 10 mod-management cfctl method handlers (`mod_subscribe`, `mod_unsubscribe`, `mod_pin_version`, `mod_unpin`, `mod_rollback`, `mod_trust_override`, `mod_conflict_resolve`, `mod_dependency_install_missing`, `mod_lockfile_export`, `mod_lockfile_import`) and registers from `cf-control/src/server.rs` via a `pub mod m33c_actions;` line plus a single `m33c_actions::register(&mut router)` call. `server.rs` itself stays a thin dispatcher; per-spec handler bodies live in their own files. Same pattern is mirrored by M33B / M33D / M37C.
- Root CA private keys are NEVER on a developer machine. Author cert signing is offline; PR-based; manual review per DR-006. The engine only ships public-key material.
- Use `ring` or `webpki` for signature verification — do NOT roll our own ASN.1. Pin the version + add a regression test against the bundled root CA.
- Load-order resolver is deterministic; do NOT use `HashMap` iteration order anywhere in the resolver. Use `BTreeMap` keyed by mod_id throughout, including conflict detection.
- Revocation list is fetched best-effort on game start (Workshop endpoint); cached locally; revocation cannot be silently un-applied (cert-pinning includes a min-ttl).
- Conflict-resolution decisions live in profile, not save — moving saves across profiles must not silently change resolutions. Validate on save load; surface mismatches in the UI.
- Workshop rollback uses content-addressed storage (`mods/.history/<sha256>/`) — multiple mods sharing assets dedupe naturally.
- Per-mod quotas are enforced at allocation site (heap), file write (disk), save bucket write (save), and end-of-tick (CPU). Do not enforce CPU only by sampling — sum exact per-script wall-clock.
- The mod browser uses M11 shell UI primitives (no bespoke widgets); accessibility per DR-012 (ACC-A) free.
- When a tier downgrade happens mid-session (e.g., a server policy refuses `experimental`), the mod's capability table is recomputed and any active capability above the new tier is revoked; offending callbacks are disabled with `script_capability_denied` events. Sim continuity preserved.
