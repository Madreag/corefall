# M36F — Anti-Cheat + Integrity Deep + Cheat Detection Heuristics + Banwave Protocols

## Status

`active`

## Intent

M36F locks the **deep anti-cheat + integrity layer** that M36 declared but did not exhaust: server-authoritative per-action validation via deterministic replay re-run with the player's input stream, three behavioral heuristics (impossible-input detection / aim-bot consistency detection / wall-hack visibility-vs-render mismatch) wired to a single confidence-scored detector pipeline, replay tampering detection via the M4B cryptographic chain-of-custody, a mod signing protocol with a cert hierarchy chained to the M33C Corefall root CA, and a four-tier graduated ban system (warning → 24 h temp → 7 d temp → permanent) with an out-of-band appeal portal. M36 shipped the anti-cheat skeleton (`cf-server-anti-cheat` foundation, three launch profiles, rate-limit hooks); M49 declared "competitive anti-cheat" as a launch GA requirement. M36F is the binding glue that proves the anti-cheat is server-authoritative, deterministic, false-positive-resistant, and operationally runnable across a 1000-account ban operation.

M36F promise: **"every reported cheater can be re-judged by replaying their inputs against the server-authoritative sim; impossible-input + aim-bot + wall-hack heuristics each carry a numeric confidence; replay bundles submitted to leaderboards are cryptographically tamper-evident; mods that affect competitive play must be signed and chain to the Corefall root CA; bans graduate through 4 tiers with an appeal portal; no admin ever needs to eyeball a clip to make a call."**

## Canonical ownership

Owns the per-action server-side validation rules, the deterministic-replay re-run validator, the three behavioral heuristic detectors + their confidence aggregator, the mod signing protocol + cert chain verifier extension on top of M33C, the banwave operations playbook + the per-account ban state machine, the appeal portal endpoint, and the `cf-server-anti-cheat` deep modules listed below. M36 keeps owning the foundation; M33C keeps owning the mod trust tier system; M4B keeps owning the bundle ledger chain; M36F binds them into a single competitive-integrity pipeline.

## Player-facing behavior

- **Server validates every action.** A player who fires a weapon, throws a grenade, or actuates a chassis joint sees the server-authoritative outcome — client predicts, server re-runs the action against the authoritative sim, mismatch results in client rollback with no visible glitch in normal play.
- **Impossible inputs get rejected at the wire.** A player whose mouse delta would imply an angular velocity > 4500 deg/s (a human ceiling per published e-sports studies) for two consecutive ticks gets that input clamped + flagged; persistent flagging triggers the heuristic detector.
- **Aim-bot consistency gets caught.** A player whose per-shot crosshair-to-target angular error has a standard deviation below the bottom 0.5 % of the human-distribution sample (collected during M36F warm-up) gets flagged with a confidence score and queued for review; legitimate top-tier players are below the threshold but rarely flagged because they still exhibit human jitter.
- **Wall-hack detection compares visibility vs render.** When a player reacts to an actor that was never visible per the server-authoritative line-of-sight sim (M22 visibility raycasts) within a reaction window (250 ms after the actor first crosses into "could-be-visible-if-rendered" state), the detector flags it.
- **Replays are tamper-evident.** A tournament replay submitted to a leaderboard ships with the M4B BLAKE3 ledger chain; the server verifies the chain on submit and rejects any bundle whose chain is broken or whose tick stream does not deterministically reproduce on a fresh sim re-run.
- **Mods can be cryptographically signed.** A modder requests a leaf cert from the Corefall intermediate CA (out-of-band, manual review), signs their `.cfmod` artifact, and the server's competitive mode whitelist accepts only mods whose leaf cert chains to the root + is not in the revocation list. Unsigned mods are demoted per M33C; competitive sessions reject them.
- **Bans graduate through 4 tiers.** First detection at confidence ≥ 0.80 issues a `warning` (visible in the player's profile + a one-time modal at next launch); second detection issues a `24h_temp`; third issues a `7d_temp`; fourth issues `perma`. Manual admin promotion can skip tiers when evidence is overwhelming.
- **Appeals route to a portal.** Every ban tier comes with a one-click "Appeal" button that opens the appeal portal URL pre-filled with the ban id; appeals carry the replay bundle the ban was based on so a human admin can re-run the validator and confirm or revert.
- **Banwave operations are batchable.** A server admin can stage N suspect account ids in a `banwave_<date>.ron` file, run the banwave validator across the batch (each one gets replay re-run + heuristic scoring), preview the verdict report, and commit the wave atomically.
- **No false-positive of a legit top player.** A pro who streams their gameplay regularly is allow-listed (per-account `competitive_allowlist: true`) and the detectors raise their thresholds by 0.15 confidence; flags below the raised threshold are absorbed silently instead of triggering a ban tier.

## Heuristic confidence thresholds (per profile)

| Profile | impossible_input flag → flag-confidence | aimbot variance → flag-confidence | wallhack reaction-window → flag-confidence | aggregator → action |
|---|---|---|---|---|
| `casual` | ≥ 0.95 (very high bar) | ≥ 0.95 | ≥ 0.95 | warning only |
| `competitive` | ≥ 0.80 | ≥ 0.80 | ≥ 0.85 | 4-tier ban ladder |
| `tournament_strict` | ≥ 0.65 | ≥ 0.65 | ≥ 0.70 | 4-tier ban ladder + manual admin review per flag |

Allow-listed accounts: each threshold raised by `+0.15` (so a `competitive` allow-listed account effectively requires ≥ 0.95 confidence to trigger anything).

## Ban tier state machine

```
                    +-------------------- evidence reverted on appeal
                    v
[clean] --flag--> [warning] --flag--> [24h_temp] --flag--> [7d_temp] --flag--> [perma]
   ^                  |                   |                    |                  |
   +- 90d clean ------+-------------------+--------------------+------------------+
                                     (auto-decay one tier per 90 clean days)
```

- `warning`: profile badge + modal at next launch; no playtime impact.
- `24h_temp`: cannot join ranked + competitive sessions for 24 h; can play unranked + offline.
- `7d_temp`: cannot join ranked + competitive sessions for 7 days; offline only.
- `perma`: cannot join any online session; offline only; appeal portal is the only path back.
- Admin can skip tiers with `--tier perma` + manual reason when evidence is overwhelming (e.g. confidence ≥ 0.99 across all three heuristics simultaneously).

## Mod signing protocol (extends M33C cert chain)

1. Modder runs `cargo run -p cf-mod -- sign request-csr <mod_dir>` — generates a CSR file with author name + mod id + public key.
2. Modder submits CSR via Corefall community PR to a curated repo (out-of-band, manual review per M33C).
3. Intermediate CA holder signs the leaf cert offline; returns `<mod_id>.crt` to the modder.
4. Modder runs `cargo run -p cf-mod -- sign artifact <mod_dir> --cert <mod_id>.crt --key <author_private.key>` — generates `mod.sig` alongside the `.cfmod`.
5. On server load: `cf-mod::cert_chain::verify(leaf, intermediate, root)` + `cf-mod::revocation::is_revoked(leaf)` runs.
6. Verified → tier promoted to `verified`; signature failure → demoted to `community`; revoked → mod refused entirely (per M33C).
7. Server in `competitive` or `tournament_strict` mode rejects any mod not in `verified` tier (or `vanilla`).

## Out of scope

- Cross-shard ban list synchronization across separate community-hosted shards (each shard is its own ban authority; M49 owns shard mesh; cross-shard ban federation is a M49 extension if/when needed).
- Machine-learning behavioral classifiers (deferred indefinitely; heuristics are explicit + auditable by design).
- Hardware-bound bans (HWID / motherboard fingerprint); the four-tier system is account-bound; hardware bans require platform SDK cooperation (M36A Steam VAC / EOS) and live in their adapters.
- Real-time client-side cheat detection on the player's machine (intentionally NOT pursued — server-authoritative validation is the entire posture).
- Voice-chat anti-toxicity moderation (separate behavioral system; not anti-cheat).
- Stream-sniping detection (out of scope; orthogonal to cheating).

## Notes for the implementer

- The validator-replay path is the heart of the milestone. It MUST run on the same deterministic sim path the client uses (per M36 determinism islands). Do NOT fork a separate validation sim — fork in a separate sim instance with the same code path. Use `cf-sim-core` directly, not a re-implementation.
- The aim-bot detector's human-distribution baseline MUST be collected during a M36F warm-up phase across opt-in volunteer competitive players (the `AntiCheatOutliers` telemetry category supports this collection). Do NOT ship a hard-coded distribution — collect the data first.
- The heuristic thresholds are configurable per profile via `content/anti_cheat/profile_thresholds.ron`; do NOT hardcode thresholds in Rust source.
- The ban state machine is `BTreeMap`-backed for determinism; do NOT use `HashMap` with default `RandomState`.
- The appeal portal endpoint is HTTP — it lives in `cf-server-anti-cheat::appeal_portal` and is gated by the same capability system as other admin endpoints (per M36 `cf-server-admin`).
- The banwave commit MUST be atomic: either every verdict in the wave applies or none does. Use `cf-server-persistence` transactional snapshot before applying + rollback on any per-account failure.
- The cert chain verifier MUST treat an expired leaf cert as a verification failure (NOT as a soft warning); allow-list expiry-soon banners are M33C's job.
- Allow-list state is sensitive — only admins with the `anticheat.allowlist.manage` capability may toggle it (per M36 capability gate).
- The validator-replay MUST short-circuit on the first byte-mismatch tick — do NOT continue the re-run beyond divergence; the mismatch tick is the evidence anchor for the audit log.
