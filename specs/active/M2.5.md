# M2.5 — Micro Reactor Defense Fun Slice

## Status

`active`

## Intent

One 60-90 second `micro_reactor_defense` scenario that proves M2 chunked terrain is fun in the player's hands: dig a trench around the reactor, hold position while one reactive enemy attacks for 60 seconds, win if the reactor survives, lose if it explodes. Win and loss both ship as scripted cfctl runs with full terrain + combat + mission events.

## Player-facing behavior

- Player spawns near a **generator core / reactor**. An **objective banner** reads "Defend the reactor for 60 seconds."
- The **reactor** is a single non-player static actor: HP, position fixed, no movement, no AI, **mission_critical=true** (per CCCP `m_MissionCritical`; cannot be gibbed instantly). It is the **predecessor of the future command-core** (DR-027 / DR-015) — the simplest defendable static actor we will ever ship. Its state surface is forward-compatible with M7+ command-core (power, shields, modules) — at M2.5 only `hp` + `max_hp` + `pressure_state` are live; the other fields are `serde(default)` placeholders.
- A **countdown timer** (default 60s = 3600 ticks at 60Hz; configurable) ticks down. The HUD timer changes color: green >30s, yellow 10-30s, red <10s. **Caption + banner warnings** fire at 30s, 15s, 5s ("30 SECONDS — HOLD" / "15 SECONDS — REACTOR STRESSED" / "5 SECONDS — HOLD THE LINE").
- One **reactive enemy guard** (reused from M1.5, unchanged) spawns and attacks. The guard picks its target (reactor vs player) using **utility scoring per DR-008**: weighted by proximity × line_of_sight × threat (player) + value (reactor). Player-aggressive guards target the player when in LOS; defensive guards target the reactor.
- **The player can dig a trench** around the reactor for cover/defense using M2's chunked terrain. The trench changes the guard's **path-cost lookups** — guard reroutes around the trench or fires over it depending on geometry. AI emits `ai.path_invalidated` when the player carves, then `ai.recovery_action` with reroute decision.
- **Reactor visual feedback** (per DR-055 + DR-003 hooks): bullet-impact **sparks** on the reactor's surface when hit; **sprite deterioration** as HP drops (4 visual states: nominal / scratched / cracked / critical / destroyed); **pressure-state HUD line** ("REACTOR: NOMINAL / STRESSED / CRITICAL / VENTING"); **explosion VFX** on destruction (debris scatter, flash, screen shake scaled by player distance + accessibility's `reduce_camera_shake_pct`).
- **HUD** shows (over M1.5's 7 zones): reactor HP bar (current/max + percent), time-remaining timer with color, player HP, guard HP (when in sight), selected item, last-event ticker, **reactor pressure** line, **objective banner** with "0/60s elapsed".
- **Win** = reactor alive when 60s timer expires AND player alive. **Lose** = reactor HP reaches 0 (`loss_reason=ReactorDestroyed`) OR player dies (`loss_reason=PlayerDead`) OR player aborts (`Aborted`).
- Both outcomes emit a structured `mission.mission_resolved` event with full `parent_event_id` cause chain (loss: reactor_destroyed → reactor_hp_changed → wound_added → projectile_hit_mo → projectile_spawned → guard's weapon_fired → ai.target_acquired (reactor) → ai.tactic_chosen).
- **Tutorial-safety** (per DR-018 + DR-023): scenarios with `tutorial_safety=true` cap reactor HP at 1 with `pressure_state=Critical` instead of destroying — gives the player a save-the-day moment without restart. M2.5 defaults to `false`.
- On loss, the HUD offers a **"show me why" prompt** that hands off to M3B replay viewer at the divergence event (the projectile that landed the killing reactor hit).
- **Difficulty presets** (inherited from M1.5): `cakewalk` / `tough_crowd` (default) / `veteran`. Veteran has a faster-firing guard + lower reactor HP.

## Acceptance criteria

### Win + loss + abort + tutorial paths

```gherkin
Scenario: Win path with trench — terrain matters
  Given a fresh micro_reactor_defense scenario at tough_crowd difficulty
  When the cfctl script micro_reactor_defense_win.cfctl.json runs
  Then the player digs a trench around the reactor (terrain.terrain_carved.count >= 100 within the trench bbox)
  And the guard fires at the reactor but the trench breaks line-of-sight intermittently
  And ai.path_invalidated fires at least 2 times (proving the AI noticed the carve)
  And the reactor survives the 60-second timer (reactor.hp > 0)
  And mission.objective_completed fires for "defend_reactor"
  And mission.mission_resolved fires with result=won, parent_event_id=<objective_completed>
  And cf-e2e --expect mission.result=won, terrain.terrain_carved.count>=100, mission.reactor_alive=true passes

Scenario: Loss path — reactor destroyed with full cause chain
  Given a fresh micro_reactor_defense scenario
  When the cfctl script micro_reactor_defense_loss.cfctl.json runs (player provides no defense)
  Then the guard fires at the reactor (no LOS-breaking cover)
  And mission.reactor_hp_changed fires N times as HP drops
  And mission.reactor_pressure_state_changed fires at 75% / 50% / 25% / 10% thresholds (Nominal → Stressed → Critical → Venting)
  And mission.reactor_destroyed fires when HP=0 with parent_event_id chain: reactor_destroyed → reactor_hp_changed (last hit) → wound_added → projectile_hit_mo → projectile_spawned → equipment.weapon_fired → ai.target_scored (reactor chosen) → ai.tactic_chosen
  And mission.mission_resolved fires with result=lost, loss_reason=ReactorDestroyed
  And cf-e2e --expect mission.result=lost, mission.loss_reason=ReactorDestroyed passes

Scenario: No-trench loss is provably faster than with-trench loss
  Given two runs: micro_reactor_defense_loss.cfctl.json (some defense) and m2.5_no_trench_loss.cfctl.json (zero defense)
  When both runs complete
  Then both result in mission.result=lost, loss_reason=ReactorDestroyed
  And the m2.5_no_trench_loss run's mission_resolved fires at an EARLIER tick than the with-defense loss
  And terrain.terrain_carved.count == 0 OR < 20 in the no-trench bundle
  And cf-e2e --expect mission.result=lost, terrain.terrain_carved.count<=20, mission.timer_remaining_ticks>=600 passes (lost with >10s left on the clock)
  (Proves M2.5-D03 "win path proves terrain matters" by inverse demonstration)

Scenario: Loss path — player dies first (reactor untouched)
  Given a fresh micro_reactor_defense scenario
  When the cfctl script m2.5_player_dies_first.cfctl.json runs (player walks into guard's LOS, stays still)
  Then the guard kills the player
  And the reactor HP is still > 0
  And mission.mission_resolved fires with result=lost, loss_reason=PlayerDead
  And cf-e2e --expect mission.result=lost, mission.loss_reason=PlayerDead, mission.reactor_alive=true passes

Scenario: Aborted — player forfeits
  Given a fresh micro_reactor_defense scenario
  When cfctl invokes act.player.abort
  Then mission.mission_resolved fires with result=aborted, loss_reason=Aborted
  And cf-e2e --expect mission.result=aborted passes

Scenario: Tutorial safety caps reactor at 1 HP
  Given a scenario with tutorial_safety=true
  When enemy fire would drop the reactor below 1 HP
  Then the reactor.hp is capped at 1, pressure_state=Critical
  And mission.mission_resolved does NOT fire with loss_reason=ReactorDestroyed
  And the player can recover the situation (kill the guard, etc.) without restart
```

## Notes for the implementer

### Architecture rules

- **Reactor is a static actor**: no movement, no AI, no ControlIntent. Use the existing `ActorState` with `ActorKind::Reactor` so cf-replay's actor snapshot path covers it — do NOT invent a parallel reactor snapshot. The reactor's `mass = f32::INFINITY` so impulses never move it; HP-only damage routing per CCCP `m_MissionCritical` pattern.
- **mission_critical=true blocks instant gib**: per CCCP `Actor.cpp` mission-critical flag, the reactor cannot be one-shot. HP only drops through accumulated normal damage; pressure_state ladder steps through Nominal → Stressed → Critical → Venting → Destroyed.
- **Reuse ReactiveGuard unchanged**: per M1.5 spec rule. Add target_selection.rs that uses utility scoring (per DR-008 lean) — NOT a new AI variant. Target switching reactor↔player happens within the existing ReactiveGuard's Engaged state.
- **Single source of truth for trench-shape threshold**: document the threshold in `content/scenarios/micro_reactor_defense.ron` as a scenario-level constant. The cfctl scripts + cf-e2e expects all reference it by name (not literal). So a future re-tune doesn't break tests.
- **Per CCCP BunkerBreach.lua proof-mission lessons**: scene-area contracts (Reactor Zone, Player Spawn, Guard Spawn, optional Extraction Zone) live in the scenario .ron; cf-mod validate enforces presence. Brain placement, attacker AI setup, win checks, objective arrows are all wired through cf-mission's typed manifest, NOT free-form script.

### Pitfalls / things that have bitten us before

- **Reactor as duck-typed actor**: don't add `if actor.kind == Reactor` branches everywhere. Use `mission_critical` flag + standard apply_damage path. Same code path for player + guard + reactor.
- **Trench threshold hardcoded**: must be a scenario-level constant. Otherwise rebalancing requires recompile + cfctl script edits.
- **Timer at 60Hz only**: at 120Hz the tick count doubles. Use seconds (real time) for the timer math, not ticks.
- **Forgetting parent_event_id for reactor_hp_changed**: M3B's cause-chain walker returns ParentMissingFromBundle. Every damage event MUST link to the projectile_hit_mo that caused it.
- **Sparks/explosion not flagged cosmetic=true**: replay determinism breaks because cosmetic particle RNG drifts cross-platform. Set `cosmetic: true` on the events.
- **Reactor never gibs**: if mission_critical=true is forgotten in the .ron, an explosion at M5.5+ could instant-gib the reactor and skip the pressure_state machine.
- **AI ignores trench**: ai.path_invalidated must fire when terrain.terrain_dirty_region_batch intersects guard's path. Without this, "terrain matters" is fake.
- **Reactor HP bar lags HUD at 120Hz**: HUD reads observation AFTER sim tick, never mid-tick. Test explicitly at 120Hz.
- **No emoji in any HUD or replay text** (project rule).
