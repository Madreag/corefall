# M36E — MMO Shard Meshing + State Handoff + Per-Shard Resource Budget

## Status

`active`

## Intent

M36E ships the **persistent-MMO authority layer** mandated by DR-035: a multi-shard mesh where each shard owns an authoritative actor list bounded by a hard resource budget, deterministic state handoff at shard boundaries when an actor moves between shards, a cross-shard event broadcast bus for shard-spanning effects (siege, weather, faction war), per-shard CPU/GPU isolation so a noisy neighbor cannot starve a peer shard, rollback at shard boundary preserving determinism across hand-off events, and consistent global time across all shards via NTP synchronization with a monotonic tick offset. M36 declared the `mmo_shard` launch mode; M36C declared the per-tick budget; M36D locked GPU/CPU determinism. M36E binds them into a network of cooperating authoritative servers that together host a persistent world without sacrificing the byte-identical replay contract.

## Canonical ownership

Owns shard topology, per-shard authority boundaries, the actor hand-off protocol, cross-shard event broadcast bus, per-shard resource budget enforcement (CPU cores, GPU microseconds, memory ceiling), shard-boundary rollback, the global-time monotonic offset, and the `cf-shard-mesh` crate. M49 PvE / PvP scale acceptance consumes this layer; M36E provides the protocol. DR-035 (MMO architecture) is partially implemented by M36E (handoff + meshing); M49 closes player-facing MMO content gates.

## Operator-facing + indirectly-player-observable behavior

- **Operator: shard topology declared in config.** `mmo_cluster.ron` declares N shards by `(shard_id, region_aabb, neighbor_shard_ids)`; the lobby directory loads + validates.
- **Operator: per-shard resource budget enforced.** Each shard declares `max_actors`, `max_projectiles`, `max_hazard_pixels`, `cpu_cores`, `gpu_us_per_tick`, `ram_mb`; exceeding any hard cap rejects new entities + emits `shard_budget_exceeded`.
- **Operator: hand-off observable.** `cfctl observe.shard.handoffs --since <tick>` returns recent actor moves: `actor_id`, `from_shard`, `to_shard`, `handoff_tick`, `state_blob_bytes`, `verified` y/n.
- **Operator: global time monotonic.** `cfctl observe.shard.global_time` returns `(global_tick, ntp_offset_us, drift_ppm)`; all shards agree on `global_tick` within ±1 tick.
- **Operator: rollback at boundary visible.** When a player's input crosses a shard boundary, both shards resimulate the affected tick range; rollback events emitted to audit log with `cross_shard: true`.
- **Indirectly-player-observable: seamless boundary crossing.** Player walking from shard A to shard B sees no loading screen and no actor pop; their actor's full state (position, velocity, inventory, status effects, ongoing animations, projectile ownership) transfers atomically within one tick.
- **Indirectly-player-observable: cross-shard line-of-fire.** A projectile fired in shard A toward an actor in shard B reaches the target with deterministic ballistics; the cross-shard event bus delivers the impact event to shard B's authoritative sim.
- **Indirectly-player-observable: shared world clock.** Day/night cycle, weather events, faction-war timers progress in lockstep across every shard; a player on shard A sees the same sunset as a player on shard B at the same wall-clock instant.
- **Indirectly-player-observable: hostile shard isolation.** A shard suffering a stress event (mod abuse, breach event, fight cluster) drops no ticks on its peer shards; per-shard CPU/GPU isolation prevents bleed.

## Acceptance criteria

```gherkin
Scenario: Shard mesh boots from topology config
  Given mmo_cluster.ron declares 4 shards with neighbor links forming a 2x2 grid
  When cf-server starts in --mode mmo_shard
  Then the mesh comes up with 4 QUIC links established (shard 0<->1, 0<->2, 1<->3, 2<->3)
  And mesh_health pingers report all neighbors healthy within 2 seconds

Scenario: Actor hand-off transfers complete state atomically
  Given an actor at position (x, y) approaching the boundary between shard A and shard B
  When the actor's position crosses the boundary AABB
  Then shard_handoff_started fires with actor_id + from=A + to=B + global_tick=T
  And shard_handoff_completed fires within 1 tick with verified=true
  And the actor's inventory, status effects, projectile ownership, and animation state are byte-identical pre and post hand-off

Scenario: Per-shard resource budget rejects overflow
  Given shard A declares max_actors=200 and currently hosts 199 actors
  When 3 actors attempt to enter shard A simultaneously
  Then 1 actor is admitted and 2 are rejected at the boundary
  And shard_budget_exceeded fires with shard_id=A resource=actors limit=200 attempted=202
  And the rejected actors remain on their origin shard

Scenario: Cross-shard projectile delivers impact
  Given a projectile fired in shard A with a trajectory crossing into shard B
  When the projectile's ballistic path crosses the boundary
  Then the broadcast bus delivers the projectile to shard B's authoritative sim
  And shard_broadcast_delivered fires with kind=projectile_handoff global_tick=T
  And the impact event resolves on shard B with deterministic damage

Scenario: Global time stays monotonic across shards
  Given 4 shards running for 600 seconds with NTP sync enabled
  When `cfctl observe.shard.global_time` is sampled every 5 seconds on each shard
  Then global_tick across shards never differs by more than 1 tick
  And drift_ppm stays below 50 ppm per shard
  And shard_clock_drift fires if any shard exceeds 100 ppm

Scenario: Shard-boundary rollback preserves determinism
  Given a player's input fires a weapon on shard A targeting an actor that hands off to shard B mid-flight
  When shard B's authoritative resolution conflicts with shard A's optimistic prediction
  Then shard_rollback_engaged fires with shards=[A,B] tick_range=[T-3, T] reason=cross_shard_conflict
  And both shards resimulate the affected range
  And the resolved state is byte-identical to a single-shard reference run of the same inputs

Scenario: Shard isolation prevents noisy-neighbor bleed
  Given shard A is stressed to 95% of its CPU budget (deliberate stress test)
  When shard A's neighbors B, C, D run normal workload concurrently
  Then shards B, C, D maintain p99 tick time within 5% of their baseline
  And per-shard cgroup metrics confirm A's CPU usage does not exceed its declared 4-core cap

Scenario: cfctl drain evacuates a shard cleanly
  Given operator runs `cfctl admin.shard.drain --shard 2 --grace 60s`
  When the drain command executes
  Then all actors on shard 2 are handed off to their nearest neighbor shard within 60 seconds
  And the broadcast bus continues delivering cross-shard events during the drain
  And after grace expires, shard 2 stops accepting new entities and emits a clean shutdown event

Scenario: Cluster determinism CI gate
  Given the CI workflow `m36e_cluster_determinism.sh`
  When a 4-shard cluster runs a 1000-tick scenario with 50 randomly hand-offing actors twice
  Then both runs produce byte-identical per-shard events.jsonl and global event order
  And the merged cluster bundle's determinism.cluster_checksum is identical run-over-run

Scenario: Mesh tolerates single-shard failure without data loss
  Given a 4-shard cluster running healthy for 5 minutes
  When shard 3 is forcibly killed (kill -9)
  Then mesh_health reports shard 3 unreachable within 2 seconds
  And actors on shard 3 are reloaded from the most recent checkpoint on a neighbor shard
  And no actor state is lost beyond the last checkpoint epoch (≤ 60 seconds of progression)
```

## Out of scope

- Cross-cluster federation (multi-region clusters with WAN-latency hand-off) — M48+ scale.
- Player-facing MMO content (quest chains, faction war progression, persistent housing) — M49.
- Dynamic shard re-meshing (live add/remove shards under load) — operator must drain + restart.
- Cross-shard PvP balance tuning — M49 PvP balance.
- Cloud auto-scaling of shards — M42 deployment ships static topology only.

## Notes for the implementer

- Shard boundaries are axis-aligned in world space; AABB declared in `mmo_cluster.ron`. Diagonal boundaries are out of scope.
- Hand-off blob format is `bincode` over the actor's full ECS component set, hashed with blake3 before send; receiver verifies hash before deserialize.
- Broadcast bus uses cf-net QUIC streams with one persistent stream per shard pair; ordering enforced by `(global_tick, source_shard_id, seq)` triple.
- Global time uses the host's NTP (chronyc on Linux, w32tm on Windows, sntp on macOS); each shard exposes its sync state via `/health`. NTP server is operator-chosen.
- Monotonic tick offset is `global_tick = wall_ntp_seconds × tick_rate + boot_offset`; boot_offset locked at cluster startup; never drifts.
- Rollback at boundary uses the M8A 6-frame rollback window; both shards rollback to the divergence tick and resimulate forward.
- Per-shard isolation on Linux uses cgroups v2 (`cpu.max`, `memory.max`, `io.max`); on macOS uses `taskpolicy` + `taskset`; on Windows uses Job Objects.
- Mesh health pinger uses cf-net QUIC PING frames at 1 Hz; 3 missed pings = mark neighbor unreachable + emit alert.
- `m36e_cluster_determinism.sh` is the canonical CI gate; runs the 4-shard reference cluster twice and diffs per-shard + merged cluster bundles. Must complete in under 30 minutes.
- The 1-hour soak (`m36e_handoff_soak.sh`) is a release-blocker for M49; not gated on M36E close, but the harness ships in M36E.
- DR-035 four-shard reference topology lives at `game/content/server/mmo_cluster.ron`; M49 may extend to 16-shard for stress testing.
