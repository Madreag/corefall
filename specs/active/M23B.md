# M23B — AI Memory + Persistent Commander Doctrine + LLM-Backed Tactical Plans

## Status

`active`

## Intent

Expand M23's stub `cf-mind` LLM layer into the **full bot-cognition body** that M7's `BotMemory.doctrine_cache` field was reserved for. M23B ships three tightly-linked pieces of depth:

1. **Per-actor `BotMemory`** — where the actor has been shot, which weapons have hurt this actor, last 10 mission outcomes; bots remember and adapt over a run.
2. **Persistent AI commander doctrine** — the M25 rival commander carries grudges + tactic preferences **across missions**; learns the player's loadout patterns; shifts squad composition + objective priorities in response.
3. **Async LLM-backed tactical plans** — the M23 5s-tick mind layer queries an LLM provider with a serialized `TacticalContext`, parses 1-3 strategic-move proposals, and feeds them into the M7 utility scorer as priors — non-blocking, sandboxed, replay-recorded.

M23B promise: **"the AI remembers; the commander adapts; the LLM whispers tactics — and not a single tick of sim ever waits for any of it."**

## Player-facing behavior

- **Per-actor pain memory** — every actor (player and bots) maintains a ring buffer of the last 32 damage events: `body_part_hit`, `weapon_kind`, `range_band`, `from_direction`. After being shot in the right shoulder by a sniper at 600u, a bot tilts cover toward that bearing and prefers a flak helmet on respawn.
- **Per-actor weapon-threat memory** — a bot ranks weapons by **threat-to-self**: weapons that have HIT this actor get +1 threat weight per hit; weapons that nearly killed (HP<10% after hit) get +5. Bots prioritize cover against high-threat shooters first.
- **Last-10-mission outcome log** — `MissionOutcomeLog { mission_id, victory, surviving_squad_pct, player_loadout_signature, dominant_kill_weapon }` retained 10 deep, persisted per save.
- **Persistent commander rivalry (M25 carry)** — the named AI commander assigned at campaign start carries `CommanderDoctrineState { player_loadout_history, preferred_counter, grudge_level }` across missions; if the player won the last 3 missions with sniper builds, the commander deploys more flankers + smoke + counter-snipers next mission.
- **Commander adaptation FSM** — 6 doctrine archetypes (`Defensive`, `Aggressive`, `Attritional`, `Asymmetric`, `Decapitation`, `Scorched`); each mission, the commander picks the archetype that historically counters the player's signature; pick is replay-recorded.
- **Async LLM tactical proposals** — every 5s of sim time per active commander (NOT per actor — gates LLM cost), the planner serializes a `TacticalContext` (current map zones, squad positions, player last-known position, casualty deltas, terrain hot tiles), POSTs to the configured provider, parses up to 3 `{ move_kind, target_zone, reason_label, confidence }` proposals into a non-blocking inbox.
- **Local AI vetoes + reason labels** — the M7 utility scorer reads the inbox each tick; high-confidence (`≥0.7`) proposals boost the matching task's utility by +0.4; low-confidence vetoed and logged with `reason_label`.
- **Fully bounded + sandboxed** — no proposal is ever applied without local-AI evaluation; LLM has no direct write to sim; rate limit is 1 round-trip per commander per 5s; quota-aware (hard halt at provider quota exhaust); offline / timeout / disabled = no-op (local AI carries on).
- **Replay-deterministic** — LLM responses are **replay-injected** (recorded with the request hash; on playback the recorded response is fed back in lieu of a live LLM call) so a replay of "the commander brilliantly flanked you" is bit-exact across machines and offline.
- **Save / load roundtrip** — `BotMemory` + `CommanderDoctrineState` + `MissionOutcomeLog` serialize into the save file (M-save kernel); load restores byte-for-byte.

## Acceptance criteria

```gherkin
Scenario: Pain memory records a damage event
  Given an enemy rifleman bot at full HP
  When the player shoots the bot's right_shoulder with a sniper_rifle at range_band=Long, direction=045°
  Then mind_bot_memory_updated fires with { actor_id, body_part_hit=right_shoulder, weapon_kind=sniper_rifle, range_band=Long, from_direction=045 }
  And the bot's pain ring buffer contains the event at slot 0
  After 32 more hits, slot 0 has been overwritten (ring buffer rolls)

Scenario: Cover selector biases toward angle-of-most-recent-pain
  Given a bot with pain memory dominated by hits from bearing 045° (3 of last 5 events)
  When the bot picks cover
  Then cover_state.cover_orientation is biased to face 045° (face the threat) or away (turn back to it)
  And cf-ai::cover_selector emits choice with reason_label=`pain_bearing_bias`
  And replay event mind_bot_memory_updated remains the only memory write of that tick

Scenario: Weapon-threat ranker promotes lethal weapons
  Given a bot has been hit by sniper_rifle 4 times (HP<10% on 2 of those)
  When mind_weapon_threat_ranked fires (per-mission-end summary tick)
  Then sniper_rifle threat_weight = 4*1 + 2*5 = 14 (top of list)
  And loadout_picker on next refit biases toward flak_helmet + sniper-spotter glasses (counters sniper_rifle)

Scenario: Mission outcome log retains 10 deep
  Given player completes 11 missions in a campaign
  When mission_completed fires on mission 11
  Then mind_mission_outcome_logged fires
  And MissionOutcomeLog length stays = 10 (oldest dropped)
  And the dropped entry was mission 1

Scenario: Commander adapts to player loadout signature
  Given player won the last 3 missions with player_loadout_signature=`sniper_heavy`
  When mission 4 boots
  Then mind_commander_doctrine_shifted fires with from=`Aggressive`, to=`Asymmetric`
  And commander deploys 2x flanker + 1x smoke-thrower + 1x counter-sniper (per `asymmetric.ron`)
  And mind_commander_loadout_counter_picked fires with counter_kind=`anti_sniper`

Scenario: Async tactical context serialization (5s tick)
  Given cf-mind enabled + provider configured + 1 commander active
  When 300 ticks (5s at 60Hz) elapse since last LLM call
  Then mind_tactical_context_serialized fires with payload (map zones, squad pos, player last-known pos, casualty delta)
  And an async HTTP request is dispatched to the provider
  And the sim continues; tick latency unchanged

Scenario: LLM proposal accepted boosts utility scorer
  Given a tactical proposal arrives: { move_kind=Flank, target_zone=zone_north_ridge, confidence=0.82, reason_label="player_predictable_route" }
  When local AI utility scorer reads the inbox
  Then the `Flank to zone_north_ridge` task gets +0.4 utility boost
  And mind_tactical_proposal_accepted fires with reason="confidence>=0.7"
  And the squad sent on that flank emits ai.doctrine_changed with reason="mind_proposal_accepted"

Scenario: LLM proposal vetoed (low confidence)
  Given a proposal arrives with confidence=0.35
  When local AI evaluates
  Then mind_tactical_proposal_vetoed fires with reason="low_confidence"
  And no utility boost applied
  And local AI continues unaffected

Scenario: LLM provider offline — local AI carries on
  Given cf-mind provider unreachable (network down OR `ai.mind.enabled=false`)
  When the 5s tick elapses
  Then NO mind_tactical_context_serialized fires
  And mind.unavailable_fallback fires once per minute (log-only, not per tick)
  And local AI utility scorer treats doctrine_cache as None (M7's documented baseline)
  And mission proceeds without observable degradation

Scenario: Quota-aware halt
  Given cf-mind has hit the configured token budget for the session
  When the next 5s tick would dispatch
  Then mind.quota_exhausted fires (once)
  And subsequent dispatches are skipped until session reset
  And local AI continues

Scenario: Replay-deterministic LLM run (record + replay)
  Given a recorded mission with 12 LLM proposals
  When the replay plays back with `ai.mind.replay_injection=true`
  Then each recorded LLM response is injected at the same tick instead of a live HTTP call
  And mind_tactical_proposal_received events match the original bit-exact
  And the mission's final state matches the original
  Without any network call

Scenario: Save / load roundtrip preserves bot memory + commander state
  Given mid-campaign save with 7 bots holding pain memory + 1 commander at doctrine=`Attritional`
  When the player saves + quits + reloads
  Then every bot's pain ring buffer + threat ranker is restored byte-for-byte
  And the commander's doctrine, grudge_level, and last-3 player_loadout_history entries restore byte-for-byte
  And no mind.* event fires during load (purely deserialization)

Scenario: cfctl dump command reveals debugger data
  Given `cfctl srv.dump_bot_memory 42` invoked
  When the server responds
  Then JSON includes pain ring buffer, weapon-threat ranking, last_doctrine_cache value
  And `cfctl srv.dump_commander_doctrine` returns the active commander's doctrine + grudge_level + last-10 mission outcomes
```

## Out of scope

- Per-actor LLM proposals (each individual bot calling an LLM) — explicitly bounded to per-commander to keep cost + quota tractable. If a per-squad layer is needed, that's a later milestone.
- Multi-LLM-vendor failover orchestration — M23B uses ONE configured provider per session; vendor-failover is M23C territory.
- Player-side LLM coaching ("the LLM whispers to YOU") — different scope; M23B is strictly enemy/commander cognition.
- Fine-tuning of LLM weights or RLHF — M23B uses off-the-shelf provider; no model training.
- Anomalous behavior detection / cheating prevention via LLM — separate cf-server-anti-cheat surface.

## Dependencies

- M7 (utility scorer + `BotMemory.doctrine_cache` field declared) — must close before consumer can read inbox.
- M22 (pathfinding) — flank / asymmetric proposals require pathing.
- M23 (cf-mind kernel stub) — must close before bot_memory / tactical_planner have a host.
- M25 (commander persona + storyteller) — `CommanderDoctrineState` rides on the persistent commander instance.
- M-save kernel — `BotMemory` + `CommanderDoctrineState` schemas serialize alongside actor state.

## Notes for implementer

- Audit first per AGENTS.md §Workflow: check `cf-mind` for any existing bot_memory or commander stub before writing fresh; the field `BotMemory.doctrine_cache` was reserved in M7 and may already be wired through `cf-ai::utility_scorer`. Read M7's source before declaring a duplicate.
- Pain memory ring buffer = `[Option<PainEvent>; 32]` + cursor; no alloc per event, deterministic eviction. Threat ranker is a `HashMap<WeaponKind, u32>` recomputed at mission end (not per tick) to avoid per-frame work.
- Commander doctrine archetypes are **data** (one RON file each, 6 total); the FSM is "given player_loadout_signature, pick best counter archetype"; the lookup table sits next to the RON files for designer tuning.
- LLM round-trip MUST be off-thread (tokio task spawn or equivalent) and must NEVER block the sim tick. Use a bounded mpsc channel for the inbox; if the channel is full (rare), drop the oldest proposal with `mind.proposal_dropped_inbox_full`.
- `TacticalContext` payload should be < 4 KB JSON; keep it concise. Provider adapters serialize this same shape regardless of vendor.
- Replay injection: at record time, write `(tick, request_hash) → response_json` to the replay sidecar; at playback, intercept the dispatch and feed the recorded response synchronously. Net result: replay never touches the network and is bit-exact.
- No `unwrap()` on parsed LLM JSON; the LLM is untrusted input. Reject malformed proposals with `mind.proposal_parse_failed`.
- No `println!` anywhere in `cf-mind` (sim-adjacent); use `tracing` per AGENTS.md.
- Quota tracking is per-session; persist remaining-budget into the save if the player wants to resume a long campaign without a fresh budget.
- The `srv.dump_bot_memory` cfctl method is debug-gated; do not expose to non-admin clients. Same for `srv.dump_commander_doctrine`.
- Replay schemas: follow `cf-replay/schemas/event/*.json` conventions; reuse `Tick`, `ActorId`, `WeaponKind`, `BodyPart`, `RangeBand`, `Bearing` shared types.
- Per AGENTS.md: no `thread_rng()` in `cf-mind` if it touches sim state (commander doctrine selection IS sim-affecting); use the seeded RNG handed in from `cf-sim-core`.
